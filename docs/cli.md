# CLI command reference

Reference detail split out of [AGENTS.md](../AGENTS.md) so it is not
auto-loaded into every agent session. Read it when you need the exact flags of a `kanban` subcommand (`kanban <cmd> --help` is authoritative).

## CLI Commands (implemented)
- Global `--project <id|name|path>` on every subcommand (overrides cwd / `$KANBAN_PROJECT`)
- `kanban init [--path P] [--copy] [--force]` - Register the folder in the store and create the board there (never a local `.kanban/`). Migrates an existing `<P>/.kanban` into the store. Repeat init is a no-op exit 0
- `kanban project list [--format table|json]` - List registered projects
- `kanban project add [PATH] [--name NAME] [--copy] [--force]` - Register a folder (migrating a local `.kanban` if present)
- `kanban project show <id|name|path>` - Show one project (id, name, work path, data root, timestamps)
- `kanban project rename <id|name> <new-name>` - Change the display name (id stays put) and write `tui.name` so the projects list shows it
- `kanban project set-path <id|name> <path>` - Repoint the work folder
- `kanban project path [id|name|path]` - Print the work path (defaults to the current project)
- `kanban project remove <id|name> [--purge] [--yes]` - Unregister; `--purge` also deletes board data. Interactive confirm unless `--yes`
- `kanban project open <id|name|path>` - Open the TUI on that project
- `kanban backup [create] [--with-artifacts] [--dir D]` - Snapshot the store (core, plus agent artifacts when asked). Prints each archive path, size, file count, and how long the locked copy took. See `docs/backup.md`
- `kanban backup list [--json] [--dir D]` - Date, kind, core/artifact sizes, retention bucket, verified or not
- `kanban backup verify <path|latest> [--dir D]` - Check hashes, parse every task, thread, and config, and refuse a newer sync format. Exit non-zero on failure
- `kanban backup restore <path|latest> [--project ID] [--mode board|full] [--identity] [--yes] [--force] [--dir D]` - Verify, take a pre-restore snapshot, then replace. `board` (default) keeps this machine's sync; `full` is disaster recovery and mints a new node id unless `--identity`. Prints what it replaces and asks `[y/N]`; `--yes` skips the question and is required when stdin is not a terminal
- `kanban backup prune [--dry-run] [--dir D]` - Apply retention
- `kanban create <title> [--backend opencode|claude|codex|omp|pi] [--model M] [--effort E] [--agent-name P] [--interactive] [--readonly] [--silence] [--designer] [--reviewer] [--orchestrator] [--chain-to TASK-NNN] [--depends-on TASK-NNN ...] [--launch-at HH:MM]` - Create task. `--readonly` makes delegated agents investigate and report through kanban4ai without changing project files, including plans or generated artifacts. `--silence` forbids questions (`kanban ask` and `kanban ask-form` are refused, and this wins over `--interactive`): the agent decides ambiguous points itself and records each dispute with `kanban suggest`. `--designer` / `--reviewer` opt this task into the project designer or reviewer bot without turning that bot on for the whole board. `--orchestrator` makes the task's first run a planning pass that decomposes it into a subtask graph (there is no board-wide orchestrator switch).
- `kanban auto-mode [on|off] [--questions decide|arbiter] [--arbiter-backend B] [--arbiter-model M] [--arbiter-effort E] [--arbiter-timeout SECONDS] [--max-resolver-runs N]` - Show or change machine-wide auto mode (`auto_mode:` in the store config, every project; see `docs/config.md`). An empty `--arbiter-*` value clears it. The hidden `kanban arbiter <id>` is what auto mode starts to answer a task's open questions.
- `kanban chain <id> [<target_id>] [--clear]` - Show, set, or clear chaining
- `kanban depends <id> [--on TASK-NNN ...] [--clear]` - Show, set, or clear the tasks `<id>` waits for. With no flags it prints the edges, whether they are satisfied, and which tasks wait on this one. `--on` replaces the whole set; every id must exist and the result must stay acyclic (a cycle is refused, naming the path). Unlike a chain, a dependency is an AND-join **and** feeds the upstream results into the task's prompt (see "Task Dependencies" in `docs/orchestration.md`)
- `kanban plan <id> --file <path> [--session <id>] [--agent]` - Submit an orchestrator plan: validate the YAML graph and create its subtasks. With `--agent` the session must be `<id>`'s current orchestrate-phase session. The whole plan is validated (unknown references, duplicate keys, cycles, unknown role profiles, `max_subtasks`) before anything is created; `kanban plan --help` carries the schema
- `kanban list` - List tasks
- `kanban show <id>` - Show task details
- `kanban take <id> --session <id> --agent` - Take task for an agent
- `kanban done <id> --session <id> --agent` - Complete task
- `kanban move <id> <column>` - Move task
- `kanban context <id> <text>` - Add a `context` message to the thread
- `kanban ask <id> <question> [--wait] [--variants TEXT ...] [--timeout SECONDS] [--session <id>]` - Add question, optionally block until answered. Refused while the task is in silence mode (`Silence: on` on `kanban show`); record the decision with `kanban suggest` instead
- `kanban ask-form <id> --file <path> [--agent] [--session <id>]` - Post one or more questions from a strict YAML form (each entry's `options` become answer variants)
- `kanban answer <id> <index> <answer>` - Answer question
- `kanban waiting <id> [--session <id>] [--eta SECONDS] [--note TEXT]` - Declare a long-running wait; records a thread note and keeps the session alive until `eta × waiting_eta_multiplier`. A pause releases the agent slot: when the deadline passes the task re-enters the queue (or, with the queue off, the agent is relaunched directly) to check the result
- `kanban detach <id> [--session <id>] [--eta SECONDS] [--note TEXT] -- <command> [args...]` - Run a command fully detached from the agent session (own `setsid` session, so it survives the tmux host being killed when the reply ends), append output to `.kanban/detached/<task>-<stamp>.log`, write the exit code to the matching `.status` file, and declare the wait in one step; the wait note carries both paths into the relaunch prompt
- `kanban questions <id>` - List open thread messages
- `kanban suggest <id> <suggestion>` - Add suggestion
- `kanban edits <id> <text>` - Set the review-edits buffer
- `kanban verdict <id> (--approve | --changes <text> [--file <path>]) --session <id> --agent` - The bot reviewer's only exit (see "Run Phases"). `--agent` is required and the session must be the task's current reviewer session on a task that is In Progress with phase `review`. `--approve` clears the phase and moves the task to human Review (chained tasks and the completion notification fire as usual); `--changes` writes the text into the `review_edits` buffer, folds it into the thread, and routes per `orchestration.reviewer.on_changes_requested`. `--file` reads the text from a file for longer write-ups; empty change text is rejected
- `kanban rerun <id> [--session <id>] [--now]` - Fold review edits into the thread and re-queue the run (the dispatcher starts it; the CLI does not pump the queue). `--now` bypasses the queue and launches immediately, as does the automatic fallback when the queue could never drain
- `kanban continue <id> --node <paired-name> [--last-published]` - Publish the source worktree WIP, release its runner, and start a fresh session on the named node with thread context; never transfers a live agent session. Requires an isolated source worktree and project git remote. An unavailable source requires explicit `--last-published` confirmation: unpublished edits are omitted and the old session cannot be stopped. JSON output reports `session` and `queued`; outbound-only targets consume the durable request through their daemon/TUI. See `docs/sync.md` §7.3.
- `kanban compact <id>` - Compact context (rule-based, no LLM)
- `kanban compact-threads [TASK-ID] [--all-projects]` - Collapse consecutive identical board-authored `agent_step` notes into one with a `×N` counter. Without arguments, process the current board; `--all-projects` processes every registered board. User/agent messages and notes referenced by replies are preserved. Writes hold the board lock; repeated runs are idempotent
- `kanban heartbeat --session <id>` - Update session heartbeat
- `kanban check-sessions` - The manual headless pump: resume expired waits, reap crashed sessions, hand due crash-restarts back to the queue (`due_restarts`), enqueue every due planned launch (`due_launches`), queue every task whose dependencies are now satisfied (`dispatch_ready_dependents`), then `dispatch_queue` and print what each step did. Ends with an `Isolation:` line — `available`, or `unavailable — <reason>` (project not registered, git not found, git too old for `merge-tree`, not a git repository, unborn HEAD, detached HEAD)
- `kanban daemon [--interval SECONDS] [--once] [--project <p>]` - Foreground loop (does not fork) that ticks every registered project: resume expired waits, reap crashed sessions, `due_restarts()`, `dispatch_ready_dependents()`, then `dispatch_queue()`. `--once` is one tick for cron or a systemd timer; the plain loop is what the user unit runs. Default interval is 60s from the store `daemon.interval` (`--interval` overrides). `flock`s `<store>/daemon.lock` and refuses a second daemon. Store-wide ticks are shared with open TUIs through `<store>/pump.lock`, so the daemon idles while a TUI pumps more often; unchanged projects with no due deadline are skipped. Automatic dispatch is skipped with `orchestration.queue_enabled: false`, but explicit local runner requests still launch directly. Missing work folders are skipped with one warning. Logs one line per resume/reap/restart/dispatch to `<store>/logs/daemon.log` and stdout. Cron fallback: `* * * * * kanban daemon --once`. Opt-in user unit: `scripts/install.sh --with-daemon` (never enabled).
- `kanban join CODE@HOST:PORT [--name NAME] [--fresh]` - Phone setup from one `serve --phone-qr` invite: sets this node to role `mobile` (name `phone` unless `--name` or already mobile; refused on a server), for a tailnet host switches `net.tailscale.mode` from off to managed and runs `net up` (installing the sidecar if missing), pairs, then runs one sync cycle. `--fresh` first moves a store that already holds projects to `<store>.pre-join-<timestamp>` (nothing is deleted) and joins with an empty store; without it, a store holding another board fails with `SYNC_STORE_MISMATCH` and a hint to rerun with `--fresh`. A login URL from `net up` means: log in, then rerun with a fresh invite if five minutes have passed. The TUI Sync → Pair with a node accepts the same invite (or the whole pasted command) with an empty code.
- `kanban serve [--port PORT]` - Foreground HTTP/1.1 server for the whole store, independent of cwd and `--project`. Uses `serve.port` (7420 by default) and binds LAN addresses selected by `sync.home_networks` plus loopback; mobile/outbound nodes bind loopback only. Public `GET /health`, `GET /version`, and `POST /pair`; other paths require a registered Bearer token. SIGINT/SIGTERM drain connections for `serve.shutdown_timeout` seconds (default 10). Sync is a star: only a `node.role: server` node accepts pairing and serves `/sync/v3/*`; clients never pair with each other (`docs/sync-server.md`). On the server: `serve --issue-token node` prints a 256-bit token once and stores its SHA-256 hash; `serve --pair-code` creates a single-use six-digit code (five minutes, five attempts); `serve --phone-qr [HOST:PORT]` prints a mobile pairing payload, the phone command `kanban4ai join CODE@HOST:PORT`, and a QR of that command (single-use code, not a bearer token); without HOST:PORT it uses this node's LAN IPv4 (default-route interface first, links that are down last), else its MagicDNS name; `serve --revoke-token SHA256` revokes a client token immediately and drops the client from `sync/hub/clients.json`. On a client: `serve --pair HOST:PORT|https://URL --code CODE` pairs with the server and writes `sync.server` plus the token in `sync/server.yaml` (0600). See [sync protocol](sync.md#11-протокол-serve). `sh scripts/install.sh --with-serve` installs `kanban4ai-serve.service` without enabling it; AUR installs it under `/usr/lib/systemd/user/`.
  In `net.tailscale.mode: system`, inbound serve additionally binds tailnet IPv4/IPv6 (including with explicit `home_networks`). `--pair HOST:PORT` and `--phone-qr HOST:PORT` also accept enabled tailnet IPs and fully-qualified MagicDNS names; pairing stores the server's MagicDNS fallback in `sync.server.urls`.
- `kanban serve --discover` / `--probe` - JSON LAN discovery of sync servers via `_kanban4ai._tcp` / availability of the configured server, with `sync.server.urls` fallback. `serve --bye shutdown|sleep` pushes the outbox and notifies the server before leaving; `serve --hello` notifies it after resume (also automatic on serve startup). Authenticated `GET /node` and `GET /nodes` expose the node card and node statuses as the server sees them. Probe configuration, durable departure state, and opt-in systemd sleep/shutdown hooks: `docs/sync.md`, “Serve 03”.
- `kanban serve` on a client replicates the store through the server automatically: push of the local outbox, then pull `after last_seq` (cursor in `sync/cursor.json`), live SSE stream with long-poll fallback, streaming NDJSON bootstrap of an empty client. Without a reachable server everything works locally and operations wait in the outbox. `serve --sync` runs one cycle and exits; `--bye` pushes the outbox first. Protocol: `docs/sync.md` section 10.
- `kanban serve --purge-relay-refs [--dry-run]` - The git relay was removed (TASK-514). This explicit command deletes this node's old `refs/kanban/sync/<node_id>` and `refs/kanban/logs/<node_id>/*` from each project's `origin`; clones made earlier keep that history. Migration only prints a hint, it never pushes deletions itself.
- TUI and `kanban daemon` run outbound sync workers without systemd, sharing a single owner with `serve` through `sync/worker.lock`. The owner sends hello on startup and bye on normal exit; daemon also handles SIGINT/SIGTERM. Peers never dial mobile nodes and report their absence neutrally as `OFFLINE`.
- `kanban net up [--auth-key-file PATH]` / `down` / `logout` / `status` / `install` - Machine-local Tailscale controls, independent of project selection. Configure `<store>/config.yaml` `net.tailscale.mode: managed|system` first (default `off`). `up` prints a login URL and terminal QR when needed; an auth-key file is deleted only after confirmed login. `status` prints Tailscale JSON including account, IPs, peer direct/DERP paths and local mode. `install` verifies the official static tarball SHA-256 before installing amd64/arm64 binaries under `<store>/net/bin`; PATH binaries take precedence. Managed sidecars are supervised by TUI/daemon/serve and stopped on exit; a standalone `net up` survives its CLI process until `net down` or a supervisor adopts it. Details and error codes: `docs/sync.md` §11.5.
  System mode is read-only: `net status` invokes the installed `tailscale status --json`; `up`, `down`, and `logout` refuse to mutate the system service. Configure its login and systemd/kernel-tun lifecycle with the administrator's Tailscale tools.
- `kanban recover <id>` - Recover crashed task
- `kanban stop <id>` - Stop the task's running agent session; the task stays In Progress (idle)
- `kanban sessions` - List active sessions
- `kanban archive` - List archived tasks
- `kanban archive-done` - Move all Done tasks to Archive
- `kanban limits [--format table|json] [--refresh]` - Remaining subscription capacity per provider (claude, codex, grok, zai, synthetic, kimi); serves the cached snapshot unless it aged out or `--refresh` is given
- `kanban limits bridge install` / `kanban limits bridge remove` - Wrap / unwrap Claude Code's statusline command with the bridge feeding the claude segment of the limits row
- `kanban stats [--compact]` - With `--compact`, cap breakdown rows using `thresholds.compact_report_top_n` and save the standard report to a printed file path. Print the application-collected usage report (tokens and time, by backend/model/project, all time / this month / this week) across every registered project — see `docs/stats.md`
- `kanban update [--check]` - Report (or install) the newest GitHub release; see "Updater". Project-independent: runs from any directory with no board. A status cached within `updates.check_interval_hours` answers from the cache, otherwise one blocking check runs; `--check` only prints the report. Without `--check` a newer release is downloaded, verified, and installed — refused with the upgrade command when pacman owns the binary
- `kanban tui` - Launch the interactive board; with no resolved project, open the projects list
- `kanban integrate <id> [--branch kanban/<id>@<node>]` - Land an isolated or received task branch into the work folder by hand (`land: manual`, or a deferred landing). Replicated results do not require a local worktree. Duplicate offline runs require an explicit `--branch` selection while the task is in Review; both branches remain available. Prints landed paths, conflicts, or the deferral reason (see `docs/sync.md` §8.2 and "Worktree Isolation").
