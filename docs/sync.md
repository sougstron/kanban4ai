# Синхронизация узлов (ноут ↔ home-server) и мобильный клиент

Спецификация эпика TASK-404 (задача «Sync 01», TASK-405). Контракт для
TASK-406…TASK-427. Локальное ядро журнала реализовано в `core/sync.rs`
(TASK-406), применение чужих операций — в `core/sync/apply.rs` (TASK-407).
Транспорт относится к следующим задачам. Если поведение расходится с документом,
сначала меняется документ.

## 1. Цели и принципы

- **База есть физически на каждом узле.** Ноут и сервер всегда хранят полную
  реплику всего store: все проекты, задачи, треды, конфиги. Деления «по
  проектам» и узла-владельца нет. Любой узел может сломаться, и данные от
  этого не пропадут.
- **Мультимастер без кнопок.** Писать может любой узел в любой момент, в том
  числе офлайн. Узлы сами обмениваются изменениями, как только видят друг
  друга. Нет ни «забрать на этот узел», ни ручного checkout/checkin.
- **Сходимость детерминирована.** Порядок доставки операций не влияет на
  итоговое состояние. Конфликт возможен только тогда, когда одно и то же поле
  одной сущности менялось на двух узлах во время разрыва. Проигравшее значение
  при этом не теряется.
- **Без пиров ничего не меняется.** Узел, у которого нет сопряжённых пиров,
  ведёт себя как сейчас. Форматы файлов задач и тредов не меняются, а
  `tests/fixtures/` остаются зелёными. Вся sync-метаинформация хранится
  отдельно, в `<store>/sync/`.
- **Только локальная сеть.** `serve` слушает только LAN-интерфейсы, внешних
  сервисов нет. Код передаётся через git (раздел 8).
- **Человек не вводит команды.** Всё управляется из Settings (вкладка Sync) и
  диалогов. CLI-подкоманды существуют для агентов, скриптов и systemd.

Термины:

| Термин | Значение |
|---|---|
| узел (node) | установка kanban4ai со своей репликой store: `laptop`, `server` |
| пир (peer) | другой узел, сопряжённый с этим |
| клиент | телефон (PWA). Реплики у него нет, он работает через API узла |
| runner | узел, на котором выполняется запуск задачи |
| операция (op) | одна реплицируемая запись в журнале узла |

## 2. Идентичность узла и store

`<store>/sync/node.yaml` машинно-локален и никогда не реплицируется:

```yaml
node_id: 6f1c…-uuid4        # стабилен, создаётся при первом запуске
name: server                # slug, уникален среди пиров; суффиксы ID (разделы 6–7)
role: server                # laptop | server — на эти значения ссылается runner
store_id: 2b9e…-uuid4       # общий для всех реплик одной базы
```

В глобальном `<store>/config.yaml` секция `node` содержит `node_id`, `name`
и `role`. При первом открытии store UUID создаётся автоматически; последующие
открытия сохраняют его. `name` — непустой lowercase slug (`a-z`, `0-9`, `-`),
роль по умолчанию `laptop`. `node.yaml` — машинно-локальная запись идентичности
и `store_id`; глобальная секция позволяет менять имя и роль, но не UUID.

- Роль уникальна среди сопряжённых узлов: один `laptop` и один `server`.
  Runner ссылается именно на роль (раздел 9).
- `store_id` создаётся вместе с первой репликой и копируется на новую при
  bootstrap (раздел 10.4). Сопрячь два узла с разными непустыми store нельзя:
  это `SYNC_STORE_MISMATCH`, и человек выбирает, какую базу оставить. Слияние
  двух независимых баз в объём эпика не входит.

## 3. Что реплицируется, а что машинно-локально

Правило по умолчанию: реплицируется всё, что описывает **доску**, и не
реплицируется всё, что описывает **процессы и пути этой машины**.

### Реплицируется

| Данные | Где лежит | Как сливается |
|---|---|---|
| Поля задач (кроме локальных ниже), включая `status`, `runner` | `tasks/<status>/TASK-N.md` | LWW по полю (5.2) |
| Создание и удаление задачи | — | create идемпотентен, delete оставляет tombstone (5.4) |
| Сообщения тредов | `threads/TASK-N.yaml` | объединение по uid сообщения, поля сообщения LWW (5.3) |
| Проект: `uid`, `id`, `name`, git-remote | `project.yaml` | LWW по полю |
| Конфиг проекта | `.kanban/config.yaml` | LWW по ключу (dotted path) |
| Глобальный конфиг, кроме локальных секций | `<store>/config.yaml` | LWW по ключу |
| Ролевые инструкции | `.kanban/instructions/<role>.md` | LWW по файлу |
| Картинки | `.kanban/assets/images/` | content-addressed blob (sha256), только добавление |
| Legacy-контекст | `.kanban/context/` | только чтение, копируется при bootstrap |
| Дескриптор запуска | `<store>/sync/meta/` | по ключу узла, пишет только runner (раздел 7) |
| Аренды блоков ID | `<store>/sync/meta/` | раздел 6 |

### Машинно-локально (никогда не уходит на пир)

| Данные | Почему |
|---|---|
| `sessions/`, pid, heartbeat-файлы | процессы этой машины |
| `.lock`, `<store>/.lock`, `daemon.lock`, `pump.lock` | flock работает только в пределах одной машины |
| `worktrees/`, `backups/` | абсолютные пути и checkout этой машины |
| `project.yaml: work_path`, `migrated_from` | у каждого узла своя рабочая папка проекта |
| `logs/`, `detached/`, `provenance/`, `forms/` | артефакты локальных запусков. Отдаются по API только для чтения (раздел 11) |
| `stats/events.jsonl` | статистика узла. Отчёт строится по узлу |
| `recent_models`, `limits.json`, кэш лимитов | зависят от логинов этой машины |
| поле задачи `session` | id локальной сессии. Наружу его заменяет дескриптор запуска |
| `rev` треда | локальный счётчик оптимистичной записи |
| `<store>/config.yaml`: секции `node`, `sync`, `serve`, `daemon`, `tui` | идентичность, пиры, сеть, интервалы, отображение |
| `<store>/sync/node.yaml`, `peers.yaml`, `tokens.yaml` | секреты, права 0600 |
| `<store>/sync/meta/allocation.json` | локальные cursors расходования ID и подтверждения peer; не копируются при bootstrap |

Реплицируемые настройки, которые ссылаются на локальные вещи (например,
`agents:` с путём к бинарю), применяются как есть. Если на узле бэкенда нет,
запуск падает с `RUNNER_BACKEND_MISSING`, а не с ошибкой синхронизации.

## 4. Журнал операций и HLC

### 4.1 HLC

Hybrid Logical Clock — это тройка `(wall_ms, counter, node_id)`, и сравнивается
она лексикографически. Правила:

- на локальной записи: `wall = max(now, last.wall)`. Если `wall` совпал с
  прошлым, то `counter + 1`, иначе `counter = 0`;
- на приёме чужой операции: `last = max(last, remote)`. Следующая локальная
  запись будет строго больше;
- последнее значение хранится в `<store>/sync/hlc` и переживает рестарт. После
  рестарта часы не уходят назад, даже если системные отстали;
- если чужой `wall_ms` опережает локальные часы больше чем на `sync.max_skew`
  (по умолчанию 5 мин), операции этого пира не применяются, а пир получает
  статус `SYNC_CLOCK_SKEW`. Иначе один узел с убежавшими часами выигрывал бы
  все LWW.

В JSON HLC записывается как `[wall_ms, counter, "node_id"]`.

### 4.2 Операция

Изменения ловятся на уровне `Storage` при атомарной записи как diff «до/после».
`core/operations.rs` при этом не меняется. Одна логическая запись — одна
операция:

```json
{"op": "6f1c…:1042",                 // (node_id, seq), seq монотонен на узле
 "hlc": [1760207776986, 3, "6f1c…"],
 "store": "2b9e…",
 "project": "<project uid>",
 "entity": "task",                    // task | message | project | config | instructions | blob | run | lease | tombstone
 "id": "TASK-405",                    // для message — uid сообщения
 "set": {"status": "review", "updated_at": "…"},
 "prev": {"status": [1760207000000, 0, "a1b2…"]},   // HLC значения, которое перезаписали
 "actor": "agent"}                    // human | agent | kanban: роль автора записи
```

- `prev` нужен для обнаружения конфликтов (5.2).
- `actor` — для аудита. Правила колонок и agent/human проверяются на узле, где
  сделана запись, а при применении на пире повторно не проверяются: пиры
  доверяют друг другу после сопряжения.

### 4.3 Журнал и вектор версий

- `<store>/sync/journal/<node_id>.jsonl` — append-only, одна операция на
  строку. Свой журнал пишет только сам узел. Чужие журналы — копии, полученные
  при синке.
- Вектор версий `{node_id: последний seq}` показывает, что узел уже видел.
  Синк — это «пришли всё после моего вектора».
- Компакция: когда все известные пиры подтвердили `seq ≥ N`, префикс журнала
  сворачивается в снапшот `<store>/sync/snapshot/` (текущие значения полей с их
  HLC плюс tombstones). Если пир просит операции старше компакции, он получает
  снапшот (10.4).
- Метаданные полей (HLC последней записи каждого поля, uid сообщений, аренды,
  дескрипторы запусков, tombstones, конфликты) лежат в `<store>/sync/meta/`, а
  не во фронтматтере задач.

### 4.4 Локальное ядро (TASK-406)

- Общая точка захвата — `storage::atomic_write_text`; `operations.rs` не
  меняется. Захватываются store-проекты (`projects/<id>/`): задачи, сообщения
  тредов, `project.yaml`, конфиг проекта, а также глобальный `config.yaml`.
  Доски старого in-place формата продолжают работать без sync-артефактов;
  после миграции в store их записи проходят через этот же захват.
- Одна запись задачи/проекта/конфига даёт одну операцию с изменёнными полями;
  запись треда даёт операции для изменённых сообщений. Удаление задачи через
  `Storage::delete_task` и исчезновение сообщения дают `tombstone`.
  Удалённый ключ в diff представлен JSON `null`; конфиги используют dotted
  paths. Смена status сравнивается со старым файлом в другой колонке, а не
  считается повторным созданием задачи.
- Дополнительно к `session` из задач исключены локальные поля изоляции:
  `worktree`, `branch`, `base_commit`, `integration`, `cleanup_retry_at`.
  У проекта не реплицируется локальная история `last_opened_at`.
- UID проектов и соответствие `MSG-NNN` → UID хранятся в
  `sync/meta/state.json`. UID нового сообщения равен op_id создания,
  `parent_id` в операции — UID родителя. `rev` и UID не добавляются в YAML
  треда. Повторное использование display-id после удаления создаёт новый UID.
- `Journal::observe` проверяет переданный лимит skew и сохраняет принятый
  HLC; после рестарта следующая запись строго больше принятой операции.
- `sync/pending.json` — durable redo-запись данных и операций под локальным
  `sync/.lock`. После неё выполняются атомарная запись данных, append + fsync
  собственного журнала, запись `meta/state.json` и `hlc`. При следующем
  открытии store незаконченная запись завершается: неполная последняя строка
  журнала отбрасывается, уже записанные op_id не дублируются. Метаданные и
  рабочие файлы записываются с fsync файла и родительского каталога.
- `Journal::state` возвращает вектор и метаданные полей;
  `Journal::compact` принимает векторы **всех** известных пиров, включая
  офлайн-пиров. Подтверждённый всеми префикс сохраняется в
  `sync/snapshot/state.json` до замены журнала оставшимся суффиксом.
  Снапшот включает значения, HLC, UID и tombstones; `compacted` отмечает
  границу, перед которой транспорт должен выдавать снапшот, а не журнал.


## 5. Слияние

Чужие операции применяет движок под board lock проекта. Применение
идемпотентно: операция с уже виденным `op` пропускается.

### 5.1 Единица слияния

Единица слияния — поле. Правка `title` на одном узле и `status` на другом в
конфликт не попадают: применяются обе.

### 5.2 LWW по полю и конфликт

Для каждого поля хранится HLC последней записи. Входящая операция по полю `f`:

1. `meta[f].hlc == op.prev[f]`: обычная перезапись, конфликта нет.
2. `meta[f].hlc > op.prev[f]` и `meta[f].hlc != op.hlc`: записи
   **конкурентные**, обе стороны меняли поле, не видя друг друга. Побеждает
   больший HLC, при равенстве `wall_ms` и `counter` — больший `node_id`.
   Проигравшее значение сохраняется:
   - запись в `<store>/sync/meta/conflicts.jsonl` (проект, задача, поле, оба
     значения, оба HLC, узлы);
   - board note в треде задачи от `kanban`: «Конфликт поля «{field}»: оставлено
     значение с {winner_node} ({winner_time}), на {loser_node} было: {loser_value}».
   Это правило симметрично: оба узла фиксируют один и тот же конфликт с одним
   победителем.
3. `op.hlc < meta[f].hlc` без конкурентности: значение устарело и молча
   игнорируется.

Конфликт снимается кнопкой «Взять другую версию» (TASK-416). Это обычная новая
запись с новым HLC, и она расходится по узлам как любая другая. Черновик
ответа `draft` сливается по LWW и конфликтов не создаёт.

### 5.3 Треды

- Сообщение идентифицируется глобальным **uid** = op_id операции, которая его
  создала. По uid треды и объединяются (расширение существующего
  `merge_threads` по id). Сообщения только добавляются. Изменяемые поля
  сообщения (`status`, `answer`, `answered_by_role`, `draft`, `body` у
  review-edit) сливаются по 5.2.
- **Отображаемый `MSG-NNN` может совпасть.** Номер выдаётся как `max + 1` по
  треду, поэтому два узла офлайн создадут два разных `MSG-053`. При слиянии
  номер оставляет сообщение с меньшим `(hlc, node_id)`, а второе
  детерминированно получает суффикс стабильного `node_id`: `MSG-053@6f1c…`.
  Имя (`laptop`/`server`) можно подставлять при отображении, не меняя идентичности.
  `parent_id` хранится в операциях как uid, поэтому ссылки на переименованное сообщение
  не ломаются. Новые номера продолжаются с `max(числовая часть) + 1`.
- Порядок сообщений в файле треда — по HLC создания.
- Компакция контекста (rule-based) выполняется на одном узле и реплицируется
  как операции: tombstones удалённых сообщений плюс новое сводное сообщение.
  На другом узле компакция того же треда не запускается повторно, пока не
  применены её операции. Порог считается по реплицированному состоянию.

### 5.4 Создание, удаление, tombstones

- Создание задачи или проекта идемпотентно по ID/uid. Повторная доставка
  ничего не меняет.
- Удаление — это операция `tombstone` с HLC. Tombstone побеждает любые
  правки поля с меньшим HLC. Правка с большим HLC, сделанная конкурентно
  (на другом узле не видели удаления), удаление **не** отменяет: удаление
  выигрывает, правка уходит в список конфликтов, и задачу можно восстановить
  кнопкой. Восстановление — явная операция `restore`.
- Tombstones не компактируются, они маленькие. Номер удалённой задачи больше
  никогда не выдаётся (раздел 6).
- Проекты: если два узла офлайн зарегистрировали разные проекты с одним slug
  `id` (разные `uid`), проект с большим `(hlc, node_id)` получает следующий
  свободный суффикс `-2`, `-3`… по существующему правилу коллизий.
  `work_path` у каждого узла свой (раздел 3). Если на узле рабочей папки нет,
  проект показывается так же, как сейчас показывается отсутствующая папка.

### 5.5 Перемещение файлов

`status` — обычное поле. Директория `tasks/<status>/` выводится из него: движок
применения переносит файл атомарно под board lock тем же путём, что и
`move_task`, но без проверки правил (они проверены на исходном узле).
Побочные эффекты колонок (auto-launch chained, resume_after_last_answer,
уведомления) срабатывают **только на runner-узле задачи**: на нём, если
запуск есть, иначе на узле, где сделана запись. Иначе каждый реплицированный
переход запускал бы агентов на обоих узлах.

### 5.6 Движок применения (TASK-407)

- `Journal::apply_remote(ops, max_skew_ms)` принимает доверенные операции одной
  базы; лимит skew передаётся из настроек вызывающим кодом. Проверки store,
  идентичности op/node, путей и локальных полей выполняются до изменения данных.
  Пока транспорт не реализован, это Rust API, не отдельная CLI-команда.
- Движок держит store lock, затем board locks в порядке путей, затем sync lock.
  Новый destination при коллизии проекта блокируется без удержания sync lock;
  старые board locks остаются удержанными. Правила автора и колонок повторно не
  вызываются, агентские запуски и уведомления здесь не выполняются.
- Сравнивается полная тройка HLC; история операций с `prev` остаётся в
  `meta/state.json`. Проверяется вся цепочка предков поля, а не только текущий
  победитель: иначе доставка третьей конкурентной ветки или пропущенного предка
  меняла бы список конфликтов. Конфликты нормализуются по паре версий; JSONL и
  board notes являются детерминированной проекцией этой истории. `draft`
  выигрывает по LWW без записи конфликта.
- Дедупликация — по `op_id`, а вектор подтверждает только непрерывный префикс:
  получение seq 3 раньше seq 1–2 не означает, что узел получил весь журнал.
  Журналы чужих узлов сохраняются отдельно; применение не порождает локальных ops.
- `sync/remote-pending.json` — fsync redo всех файлов и sync-метаданных.
  Открытие store и чтение состояния завершают незаконченный redo под теми же
  locks. Запись рабочих файлов обходит локальный capture. Локальные поля
  существующей задачи, конфигов и проекта сохраняются.
- До получения обязательных полей создания дельты остаются в метаданных:
  неполный task/project не публикуется. Новый проект имеет пустой локальный
  `work_path` и отображается как проект без рабочей папки. Разные UID с одним
  slug сортируются по HLC создания; суффиксы не занимают исходные slug других
  известных проектов.
- Сообщения строятся по UID и объединяются существующим `merge_threads` по
  display-id после назначения детерминированных алиасов. В коллизиях суффикс
  содержит стабильный `node_id`: wire op не содержит имя узла, а локальное имя
  нельзя использовать для сходящейся проекции. Ссылки на родителей переводятся
  из UID после полного назначения алиасов. Числовая часть `MSG-NNN@node_id`
  учитывается при выдаче следующего номера. `rev` увеличивается при изменении
  сообщений, но остаётся машинно-локальным и не входит в свойство сходимости.
- Tombstone удерживает удаление независимо от более нового edit; edit сохраняется
  в конфликте. Явный `restore` с HLC выше tombstone восстанавливает сохранённые
  значения. История tombstones и причинные версии не удаляются при компакции
  журнала; snapshot сохраняет их вместе с полями.
- `tests/sync_apply_test.rs` перебирает все 720 порядков доставки создания,
  трёх конкурентных веток и причинного продолжения, а также все перестановки
  сценариев сообщений, удалений и коллизий проектов. Проверяются поля, clocks,
  конфликты и сообщения (без локального `rev`), повторная доставка, сохранность
  локальных полей, stale writer и завершение redo.


## 6. Аренда блоков ID задач

Сейчас `Storage::get_next_id` возвращает `max + 1`. Два офлайн-узла выдали бы
один и тот же `TASK-N`, а ветки `kanban/TASK-N` столкнулись бы.

- Каждый узел держит арендованный блок номеров на проект:
  `lease {project, node, from, to}` — реплицируемая операция `entity: lease`.
  Размер блока — `sync.id_block` (по умолчанию 50).
- Новый блок берётся, только когда пир онлайн и подтвердил текущий вектор.
  Начало блока = `max(конец всех известных аренд, max существующего ID) + 1`.
  Блок считается выданным, когда пир применил операцию аренды. Офлайн новые
  блоки не берутся.
- Предвыборка: если в текущем блоке осталось меньше половины номеров, узел
  заранее берёт следующий блок. Так у узла почти всегда есть запас на офлайн.
- Номера выдаются по возрастанию внутри своих блоков и не переиспользуются.
  Удалённые номера закрыты tombstone.
- **Исчерпание блоков:** создание задачи отказывает с
  `SYNC_ID_BLOCK_EXHAUSTED` до reconnect и подтверждённого продления аренды.
  Узел не выдаёт номера за пределами своих блоков: это сохраняет уникальность
  `TASK-NNN` и веток `kanban/TASK-N` без переименования при слиянии.
- Миграция существующих досок: при первом сопряжении узел-источник bootstrap
  выдаёт себе блок, начиная с `max + 1`, а пиру — следующий.
- Сообщения тредов блоков не арендуют (5.3).

### 6.1 Локальный API аренды (TASK-408)

- `Journal::prepare_id_leases(project_alias, peer_node_id, peer_vector,
  peer_remaining)` вызывается на bootstrap-источнике после обмена журналами.
  `peer_vector` должен подтверждать весь текущий локальный вектор. Источник
  остаётся единственным выдающим блоки для этого проекта: два независимых
  `max + 1` при одновременном продлении недопустимы.
- Первый вызов выдаёт источник → пир два последовательных блока над максимумом
  имён существующих файлов задач, известных созданий и task-tombstones.
  Размер читается из локального `<store>/config.yaml: sync.id_block`, по
  умолчанию 50; требуется положительное целое. Повторный вызов продлевает
  только блоки с остатком строго меньше половины размера (для нечётного
  размера — меньше `ceil(id_block / 2)`).
- Результат — immutable операции `entity: lease`, `id = op_id`,
  `set = {node, from, to}`; `project` — UID проекта. Транспорт применяет их
  через `apply_remote` на пире и передаёт его новый вектор в
  `confirm_id_leases(peer_node_id, peer_vector)`. Свои блоки источник не
  расходует до подтверждения; пир может расходовать полученный блок после
  durable применения. Потерянный ответ повторно возвращает те же операции,
  а не выдаёт дополнительные блоки. Перекрывающиеся блоки и аренды второго
  источника отклоняются с `SYNC_LEASE_CONFLICT`.
- `remaining_task_ids(project_alias)` возвращает доступный этому узлу остаток
  для handshake предвыборки. Транспорт и bootstrap относятся к следующим
  задачам эпика; до первого разрешения аренды bootstrap должен завершить
  копирование проекта и не допускать локальное создание задач на новом пире.
- `Storage::get_next_id` на арендованной доске **расходует** номер: cursor
  сохраняется атомарно до возврата ID. Сбой записи задачи оставляет пропуск,
  но не позволяет повторить номер. Локальные cursors и подтверждения в
  `sync/meta/allocation.json` не реплицируются и не копируются при bootstrap;
  операции аренды и tombstones остаются в `meta/state.json` и snapshot после
  компакции. Фронтматтер, `TASK-NNN` и `kanban/TASK-N` не меняются.
- Без аренд сохраняется прежний `max + 1`, включая in-place доски без
  sync-артефактов. При миграции не восстанавливаются номера, удалённые ещё до
  появления журнала: этой истории в старой доске нет.


## 7. Запуски: локальное состояние против дескриптора

Сессия, pid, heartbeat, worktree и `task.session` остаются на runner-узле.
Наружу реплицируется **дескриптор запуска**, по одному на узел:

```yaml
# <store>/sync/meta/<project>/runs/TASK-405.yaml
runs:
  server:                       # ключ — имя узла; запись в него делает только этот узел
    gen: 3                      # поколение: max(gen всех ключей) + 1 на момент старта
    state: running              # queued | running | waiting | finished | failed
    phase: executor
    started_at: …
    branch: kanban/TASK-405
    heartbeat: …                # прорежен: не чаще раза в sync.run_heartbeat (60 с)
    code: null                  # код падения из раздела 13.2
```

- Каждый узел пишет только свой ключ, поэтому конфликтов по дескриптору нет.
- Пир показывает «выполняется на сервере» и **не** делает reap или
  crash-detect чужих сессий. Падение runner-узла пир видит через статус узла
  (раздел 12) и проставляет коды `RUN_NODE_*` от имени `kanban` в треде, но
  сам дескриптор не меняет.
- Очередь, слоты и лимиты конкурентности — на runner-узле.
- **Защита от двойного запуска онлайн.** Запуск всегда выполняет сам
  runner-узел (локально или через `POST …/launch`). Перед стартом он проверяет
  дескрипторы: если у другого узла `running/waiting/queued` и тот узел в сети,
  запуск отклоняется с `RUN_ALREADY_RUNNING`.
- **Двойной запуск при разрыве** не предотвращается (узлы не видят друг
  друга), а обнаруживается после слияния: в дескрипторе два ключа с
  одинаковым `gen`. Подробности в сценарии 14.3.

## 8. Код: git между узлами

- Клон проекта на пире создаётся и обновляется автоматически. Если у проекта
  есть remote, клон идёт через него, иначе через `git bundle` по `serve`
  (`/git/…`, раздел 11). ssh-ключи не нужны.
- Перед запуском на другом узле live-снапшот рабочей папки, включая
  незакоммиченную работу (`commit-tree`), передаётся как
  `refs/kanban/integration`. Тогда `seed: live` на runner-узле видит то, что
  есть у человека на ноуте.
- После завершения запуска ветка `kanban/TASK-N` передаётся на пир, и код
  физически оказывается на обоих узлах. Landing в рабочую папку каждого узла
  выполняется существующим механизмом. Если не получилось, бейдж «ожидает
  landing на {node}».
- Ветка из запуска на «чужом» узле при двойном запуске называется
  `kanban/TASK-N@<node>`.

## 9. Runner

- `runner: server | laptop | auto` на трёх уровнях: глобально (`runner.default`,
  реплицируется), в проекте (`inherit | server | laptop | auto` через новую
  `InheritGroup::Placement` в `core/config.rs`), в задаче (поле `runner`,
  `inherit` по умолчанию). Без пиров runner игнорируется, и запуск идёт
  локально.
- `auto` = сервер, если его статус `ONLINE`, иначе этот узел.
- Колбэки агента (`$KANBAN_CMD`) пишут в реплику runner-узла, а синк разносит
  изменения дальше. Ноут можно выключить посреди задачи.
- **Подсказки появляются только при запуске.** Если выбранный runner
  недоступен, вместо ошибки открывается диалог (TUI и тот же ответ API для
  PWA, TASK-420): код и текст причины (раздел 13) и кнопки
  `[Запустить на {другой узел}] [Ждать {узел} в очереди] [Разбудить сервер]* [Отмена]`.
  `*` — только если недоступен узел с `wol` (раздел 12.3). Других
  всплывающих подсказок нет.

## 10. Транспорт синхронизации

### 10.1 Когда синкаться

Синк полностью автоматический, вызывается из `serve`/`daemon` и работает без
открытого TUI. Поводы:

- старт узла и выход из сна (отправляется `hello`);
- пир появился в mDNS или ответил на probe;
- каждая локальная запись: push в живой поток;
- периодический pull раз в `sync.interval` (по умолчанию 30 с), страховка от
  потерянных событий.

### 10.2 Протокол обмена

1. `GET /sync/vector`: узнать вектор пира.
2. `GET /sync/ops?after=<свой вектор>`: получить недостающее страницами,
   применить (раздел 5).
3. `POST /sync/ops`: отправить то, чего нет у пира.
4. `GET /sync/stream` (SSE): пока оба онлайн, операции идут живым потоком.
   После обрыва соединения — снова шаг 1.

Сначала применяются аренды и tombstones, потом остальное. Порядок внутри
страницы — по HLC.

### 10.3 Выключение и сон

Хуки systemd (shutdown, sleep) вызывают `POST /sync/bye {reason, at}` на всех
пирах, предварительно протолкнув хвост журнала. Пир запоминает «ушёл в
{at}». По этой отметке `NODE_POWERED_OFF` и отличается от
`NODE_UNREACHABLE`. После старта или пробуждения узел шлёт `hello` (обычный
`/sync/vector` с отметкой), и отметка «ушёл» снимается.

### 10.4 Bootstrap новой реплики

Пустой узел после сопряжения получает полный снапшот store
(`GET /sync/snapshot`: архив store без машинно-локальных данных + `store_id` +
вектор + meta) и дальше синкается обычным образом. Блоки ID выдаются по
разделу 6. Если оба узла непустые и `store_id` разный, это
`SYNC_STORE_MISMATCH`.

## 11. Протокол `serve`

`kanban4ai serve` — подкоманда того же бинаря, отдельного Cargo target нет.
Устанавливается как systemd user-unit (пакеты AUR, `install.sh`).

### 11.1 Сеть и версия

- HTTP/1.1. Bind только на адреса из LAN-подсетей `sync.home_networks` (CIDR).
  Без них bind — на адреса приватных диапазонов. На loopback serve отвечает
  всегда. Порт `serve.port`, по умолчанию `7420`.
- mDNS: сервис `_kanban4ai._tcp`, TXT `node_id`, `name`, `role`, `proto`.
  Статические адреса пиров в `peers.yaml` — запасной вариант.
- Версия протокола — целое число `proto` (сейчас `1`). Узел объявляет
  `proto` и `min_proto`. Пиры совместимы, если версии каждого попадают в
  диапазон другого, иначе `NODE_VERSION_MISMATCH`.
- Клиентский API — `/api/v1/…`. В `v1` разрешены только добавления
  (новые эндпоинты и поля, неизвестные поля клиент игнорирует). Ломающее
  изменение — только `/api/v2` с сохранением `v1` на переходный период. Это
  нужно для будущего нативного клиента.

### 11.2 Аутентификация

- `Authorization: Bearer <token>`. Токен — 256 бит случайных данных. На узле
  хранится только хеш (`tokens.yaml`, 0600).
- Два вида токенов: **node** (пир: синк, git, API) и **client** (телефон:
  только `/api/v1` и `/events`, без `/sync` и `/git`).
- Сопряжение (TASK-411):
  - ноут ↔ сервер: одноразовый 6-значный код, живёт 5 мин, не больше 5
    попыток. `POST /pair {code, node_card}` возвращает node-токены в обе
    стороны;
  - телефон: QR с `{address, port, node_id, client token}`. Токен создаётся при
    показе QR.
- Отзыв токена делается в UI вкладки Sync. Отозванный токен получает
  `401 NODE_AUTH_FAILED`.
- TLS нет (только LAN). Это осознанный риск: токен виден в сети, к которой
  есть доступ только у владельца. Web Push по этой причине недоступен (11.5).

### 11.3 Эндпоинты

Без токена:

| Метод | Путь | Ответ |

Карточка узла (node или client):

Синк (только node):

```json
{"error": {"code": "NODE_POWERED_OFF", "node": "server", "since": "…",
           "message": "Сервер выключен с 02:13"},

                  {"action": "queue_wait", "node": "server"},
                  {"action": "wake", "node": "server"}]}
```

### 11.4 Формат ошибок

Любая ошибка возвращается так:
`{"error": {"code", "message", "node"?, "since"?, "last_seen"?, "details"?}}`.
`message` — готовый текст для UI из раздела 13 с подставленными значениями.
Клиент показывает `message`, а логику строит по `code`.

| HTTP | Когда |
|---|---|
| 400 | неверный запрос |
| 401 | `NODE_AUTH_FAILED` |
| 403 | правило колонок/ролей (текст ошибки operations как есть) |
| 404 | нет проекта/задачи |
| 409 | `RUN_ALREADY_RUNNING`, runner недоступен (`NODE_*`), `SYNC_STORE_MISMATCH` |
| 426 | `NODE_VERSION_MISMATCH` |
| 502/504 | проксирование на пир не удалось (`NODE_*` пира) |

### 11.5 Мобильный клиент

Только PWA, которую раздаёт сам `serve` из того же репо (TASK-425/426).
Нативный Android отложен. API выше держится стабильным, чтобы нативный
клиент позже работал без изменений сервера.

- Телефон хранит список сопряжённых узлов с приоритетом (по умолчанию ноут,
  затем сервер) и переключается при недоступности, показывая код причины.
- Реплика полная на каждом узле, поэтому запись идёт в узел, к которому
  подключён телефон. Запуск уходит на runner задачи.
- Web Push нет: по http в LAN нет secure context. Уведомления — только пока
  PWA открыта (SSE `/events`).

## 12. Статус узла

### 12.1 Probe

Probe идёт по порядку, первый сработавший шаг даёт код:

1. Этот узел сам вне `sync.home_networks` → у всех пиров `NODE_OUT_OF_LAN`, к
   ним не обращаемся.
2. Есть отметка `bye` и с тех пор контакта не было → `NODE_POWERED_OFF`.
3. TCP connect: отказ (RST) → `NODE_SERVICE_DOWN`. Таймаут
   (`sync.probe_timeout`, 3 с) → `NODE_UNREACHABLE`.
4. `/version` несовместим → `NODE_VERSION_MISMATCH`.
5. `/node` возвращает 401 → `NODE_AUTH_FAILED`.
6. `store_id` другой → `SYNC_STORE_MISMATCH`.
7. Часы расходятся больше `max_skew` → `SYNC_CLOCK_SKEW`.
8. Иначе `ONLINE`.

### 12.2 Карточка узла

Это `GET /node`, пир кэширует её в `peers.yaml`. Поле `wol` есть только у узла
с ролью `server`:

```yaml
wol:
  mac: "a8:a1:59:xx:xx:xx"      # MAC LAN-интерфейса хоста, который будится
  broadcast: "192.168.0.255"    # куда слать magic packet
  port: 9                       # необязательно, по умолчанию 9
```

Пир хранит последнюю карточку, поэтому разбудить узел можно, когда тот уже
выключен.

### 12.3 Wake-on-LAN (TASK-427)

- Кнопка `[Разбудить сервер]` появляется при статусе `NODE_POWERED_OFF` или
  `NODE_UNREACHABLE` у узла с `wol`: во вкладке Sync и в диалоге раздела 9.
  У ноута такой кнопки нет.
- `POST /nodes/<id>/wake` → узел, принявший запрос, шлёт magic packet в
  свою LAN и отвечает `202`. Статус узла становится «Будим сервер…» до
  появления узла или до таймаута `sync.wake_timeout` (180 с). По таймауту —
  `NODE_WAKE_FAILED`.
- Если узел, принявший запрос, сам вне LAN, ответ — `409 NODE_OUT_OF_LAN`.
- Опция `sync.auto_wake` (по умолчанию выкл): будить автоматически, если
  задача стоит в очереди «ждать сервер».

## 13. Коды ошибок и тексты для UI

`{node}` — человеческое имя узла в именительном падеже с заглавной буквы
(«Сервер», «Ноут»; берётся из роли, иначе `name`). Время — локальное, `HH:MM`;
если не сегодня, то `DD.MM HH:MM`. `{ago}` — «3 мин назад». Эти тексты
используют TUI, API (`message`) и PWA.

### 13.1 Узлы и синхронизация

| Код | Когда | Текст для UI | Что предлагает UI |
|---|---|---|---|
| `NODE_POWERED_OFF` | узел объявил выключение или сон (`bye`) | «{node} выключен с {since}» (для сна: «{node} спит с {since}») | разбудить (если есть `wol`), запустить на другом узле, ждать |
| `NODE_UNREACHABLE` | не отвечает, предупреждения не было: аварийно выключен, спит или вне сети | «{node} не отвечает. Последний контакт: {last_seen} ({ago})» | то же |
| `NODE_OUT_OF_LAN` | этот узел сам вне домашней сети | «Вы вне домашней сети — {node} недоступен. Изменения сохранятся и уйдут при возвращении» | работать офлайн, запустить локально |
| `NODE_SERVICE_DOWN` | хост отвечает, kanban4ai serve не запущен | «{node} включён, но kanban4ai на нём не запущен» | включить «Сервер API» на том узле |
| `NODE_AUTH_FAILED` | токен отозван или узел не сопряжён | «{node} не принимает этот узел: сопряжение отозвано или не выполнено» | `[Сопрячь заново]` |
| `NODE_VERSION_MISMATCH` | несовместимые `proto` | «На {node} несовместимая версия kanban4ai ({their_version}, здесь {our_version}). Обновите {older}» | — |
| `NODE_WAKE_FAILED` | magic packet отправлен, узел не появился за `wake_timeout` | «Не удалось разбудить {node}: он не появился в сети за {timeout}. Проверьте питание и Wake-on-LAN в BIOS» | повторить, запустить на другом узле |
| `SYNC_CLOCK_SKEW` | часы пира убежали больше `max_skew` | «Часы на {node} расходятся с этим узлом на {skew}. Синхронизация приостановлена — включите NTP» | — |
| `SYNC_STORE_MISMATCH` | у пира другая непустая база | «На {node} другая база kanban4ai. Выберите, какую оставить» | `[Оставить эту]` `[Взять с {node}]` (с подтверждением) |

Статус синка в шапке (TASK-416, не коды):

- «Синхронизировано с {node} {ago}»;
- «Офлайн с {since}, {n} операций ждут отправки»;
- «Синхронизация: получено {k} из {n}»;
- при проблеме — текст кода из таблицы.

Счётчик «Конфликтов: {n}» ведёт в список.

### 13.2 Запуски

Пишутся в дескриптор запуска (`code`), в тред от `kanban` и на карточку.

| Код | Когда | Текст для UI | Дальше |
|---|---|---|---|
| `RUN_NODE_POWERED_OFF` | runner объявил выключение или сон посреди запуска | «Прервано: {node} выключился в {at}» | при возвращении узла — crash-restart по существующим правилам; иначе `[Перезапустить на {other}]` |
| `RUN_NODE_UNREACHABLE` | heartbeat дескриптора пропал без `bye` дольше порога crash-detect | «Нет связи с {node} с {last_seen}: запуск мог прерваться» | то же; если узел вернулся и сессия жива, код снимается |
| `RUNNER_BACKEND_MISSING` | на runner нет бэкенда или он не залогинен | «На {node} нет {backend} или он не залогинен» | `[Запустить на {other}]` |
| `RUNNER_REPO_MISSING` | на runner нет клона проекта или снапшота | «На {node} нет копии проекта {project}» (снапшот: «…не получен снимок рабочей папки») | повторить после синка git, `[Запустить на {other}]` |
| `RUN_ALREADY_RUNNING` | попытка второго запуска, пока активен запуск на другом узле онлайн | «Задача уже выполняется на {node} с {since}» | `[Открыть]` `[Остановить там]` |
| `RUN_DUPLICATE` | после слияния найден двойной запуск, сделанный во время разрыва | «Задачу запускали и на {node_a}, и на {node_b}, пока узлы не видели друг друга. Сохранены обе ветки — выберите в Review» | выбор ветки в Review |

Если runner недоступен **в момент запуска**, это не код запуска: диалог
раздела 9 показывает соответствующий `NODE_*`.

## 14. Сценарии

### 14.1 Ночь на сервере → утро на ноуте

1. Вечером на ноуте задачи ставятся с runner = server (или `auto`). Запуск
   уходит на сервер. Ноут засыпает и шлёт `bye`.
2. Ночью сервер работает: колбэки агентов пишут в его реплику, журнал сервера
   растёт. Ноут на вкладке Sync сервера показывает «Ноут спит с 23:40».
3. Утром ноут просыпается и шлёт `hello`. По `/sync/ops?after=…` он получает
   ночные операции, затем `kanban/TASK-N` через `/git/…/bundle`; landing
   выполняется в рабочую папку ноута. Шапка: «Синхронизировано с Сервер 2 с
   назад». Нажимать ничего не нужно.
4. Если человек начал править раньше, чем закончился догон, ничего не
   блокируется: правки разных полей сливаются, конфликт возможен только по
   одному и тому же полю.

### 14.2 Поездка офлайн

1. Ноут вне дома, у сервера статус `NODE_OUT_OF_LAN`. Шапка: «Офлайн с 18:02,
   14 операций ждут отправки».
2. Новые задачи получают номера из арендованного блока ноута. Ответы,
   правки и сообщения пишутся в журнал ноута.
3. Запуск задачи с runner = server открывает диалог «Вы вне домашней сети —
   Сервер недоступен» и кнопки `[Запустить на ноуте] [Ждать сервер в
   очереди]`.
4. Сервер всё это время продолжает свои задачи.
5. Дома узлы видят друг друга и обмениваются журналами. Новые задачи и
   сообщения обеих сторон просто появляются. Совпавшие `MSG-NNN` получают
   суффикс (5.3). Если поле одной задачи меняли обе стороны, выигрывает поздняя
   правка, а проигравшая видна в треде и в списке конфликтов с кнопкой «Взять
   другую версию».
6. Задачи, ждавшие сервер в очереди, уходят на сервер.

### 14.3 Двойной запуск задачи

- **Узлы в сети.** Второй запуск отклоняется с `RUN_ALREADY_RUNNING` (раздел 7).
- **Во время разрыва.** TASK-N запущена и на ноуте, и на сервере. Каждый
  узел пишет свой ключ дескриптора, конфликта по нему нет.
  1. После слияния в дескрипторе два запуска одного поколения → `RUN_DUPLICATE`
     на карточке и в треде.
  2. Если оба ещё идут, оба продолжают работать. На карточке «выполняется на
     двух узлах» и кнопки остановить один из них.
  3. Ветка сервера — `kanban/TASK-N`, ветка ноута — `kanban/TASK-N@laptop`.
     Правило: без суффикса остаётся ветка запуска с меньшим `(hlc старта,
     node_id)`. Обе ветки передаются на оба узла.
  4. `status` задачи сливается по LWW. В Review человек выбирает ветку для
     landing, вторая остаётся до Done или abandon.

### 14.4 Выключение runner посреди задачи

- Сервер штатно выключили: `bye` → у запуска `RUN_NODE_POWERED_OFF` «Прервано:
  Сервер выключился в 03:40».
- Сервер пропал без `bye`: `RUN_NODE_UNREACHABLE`.
- Сервер вернулся: crash-restart по существующим правилам
  (`orchestration.auto_restart`), иначе предложение перезапустить на ноуте.
