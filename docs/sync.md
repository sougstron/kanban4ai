# Синхронизация узлов: laptop / server / mobile

Спецификация эпика TASK-404 (задача «Sync 01», TASK-405; план v3 — TASK-428,
правка документа — TASK-429). Контракт для TASK-406…TASK-442. Локальное ядро журнала реализовано в `core/sync.rs`
(TASK-406), применение чужих операций — в `core/sync/apply.rs` (TASK-407),
транспорт — в `core/sync/transport.rs` и `cli/serve/sync.rs` (TASK-413). Если поведение расходится с документом,
сначала меняется документ.

## 1. Цели и принципы

- **База есть физически на каждом узле.** Ноут, сервер и телефон всегда хранят
  полную реплику всего store: все проекты, задачи, треды, конфиги. Деления «по
  проектам» и узла-владельца нет. Любой узел может сломаться, и данные от
  этого не пропадут.
- **Мультимастер без кнопок.** Писать может любой узел в любой момент, в том
  числе офлайн. Узлы сами обмениваются изменениями, как только видят друг
  друга. Нет ни «забрать на этот узел», ни ручного checkout/checkin.
- **Сходимость детерминирована.** Порядок доставки операций не влияет на
  итоговое состояние. Конфликт возможен только тогда, когда одно и то же поле
  одной сущности менялось на двух узлах во время разрыва. Проигравшее значение
  при этом не теряется.
- **Без включённого sync ничего не меняется.** Пока `sync::enabled` ложен
  (нет пиров, нет `relay_remote`, нет явного `sync.enabled: true`), команды
  не создают `<store>/sync/`, не пишут журнал и не делают сетевых попыток.
  Форматы файлов задач и тредов те же, что в 0.7.6; `tests/fixtures/` остаются
  зелёными. Включённый позже sync — только канал обмена, не условие работы.
- **Транспорты по приоритету.** Пир достигается первым доступным путём:
  LAN напрямую → tailnet (Tailscale: system на server/laptop, managed через
  SOCKS5 на телефоне, раздел 11.5) → git-relay через remote проекта
  (раздел 10.6) → автономная работа. Отсутствие пути — не ошибка, а статус
  пути (раздел 12); `NODE_OUT_OF_LAN` означает только «LAN-пути нет».
  Код передаётся через git (раздел 8).
- **Человек не вводит команды.** Всё управляется из Settings (вкладка Sync) и
  диалогов. CLI-подкоманды существуют для агентов, скриптов и systemd.

### Local-first: sync выключен / включение позже / офлайн

Предикат один: `sync::enabled(store)` в `core/sync/format.rs`.

- `sync.enabled: false` выключает журнал даже при пирах (kill-switch).
- `sync.enabled: true` включает журнал до первого pairing (сервер, тесты).
- ключа нет — авто: непустой `sync.peers` или непустой `sync.relay_remote`.
  Позже сюда же добавляется `sync.server`.
- нет `config.yaml` или он не парсится — выключено. `solo_store` (прунинг)
  этот ключ не смотрит.

`sync/node.yaml` — личность узла. Её создают pairing, join, `serve` и явный
`Journal::open`, не обычная запись доски. Маркер `sync/armed` (пустой файл
рядом с журналом, не в `sync/meta` и не в снимке) значит: индекс drift
совпадает с диском, capture может писать дельту. Его ставит успешный
`reconcile`. Пока маркера нет, запись идёт мимо журнала.

`sync::activate(store)` при включённом sync открывает журнал и делает
`reconcile`. Без индекса это первичный снимок белого списка (задачи, треды,
конфиги, `instructions/`, `assets/images/`). `context/` и прочие `assets/`
остаются только на этой машине. Activate вызывается при старте CLI, после
pairing/join и когда воркер видит, что sync включён. Старый dev-store 0.8
с `node.yaml` и без пиров после апгрейда считается выключенным: каталог
`sync/` не трогается, маркера нет; включение позже сверяет устаревший индекс.
Недописанный `sync/intent.json` доделывается на старте CLI даже при выключенном
sync.

Пир недоступен — не ошибка записи. create/move/edit/thread/delegate с
`runner=auto` остаются локальными, операции копятся в сегментах и уходят
существующими воркерами или `kanban serve --sync`, когда связь есть. Явный
удалённый runner, которого не достучаться, CLI ставит в очередь (`runner_request`,
exit 0, предупреждение в stderr). Без git remote очередь невозможна:
`SYNC_NO_REMOTE` и подсказка `--runner <local>`, задача не меняется. Диалог
TUI «Ждать сервер» по-прежнему спрашивает человека. `once` и catch-up на этом
пути ограничены коротким таймаутом и не держат команду request-timeout'ом.

Термины:

| Термин | Значение |
|---|---|
| узел (node) | установка kanban4ai со своей репликой store: `laptop`, `server`, `mobile` |
| пир (peer) | другой узел, сопряжённый с этим |
| mobile | телефон с Arch в proot: полноценная реплика, работает офлайн, только исходящие соединения (2.1) |
| путь (path) | чем сейчас достижим пир: LAN, tailnet direct, tailnet DERP, relay или нет связи (12) |
| runner | узел, на котором выполняется запуск задачи |
| операция (op) | одна реплицируемая запись в журнале узла |

## 2. Идентичность узла и store

`<store>/sync/node.yaml` машинно-локален и никогда не реплицируется:

```yaml
node_id: 6f1c…-uuid4        # стабилен, создаётся при первом запуске
name: server                # slug, уникален среди пиров; суффиксы ID (разделы 6–7)
role: server                # laptop | server | mobile — на эти значения ссылается runner
store_id: 2b9e…-uuid4       # общий для всех реплик одной базы
dial: inbound               # inbound | outbound; mobile всегда outbound
```

В глобальном `<store>/config.yaml` секция `node` содержит `node_id`, `name`
и `role`. При первом открытии store UUID создаётся автоматически; последующие
открытия сохраняют его. `name` — непустой lowercase slug (`a-z`, `0-9`, `-`),
роль по умолчанию `laptop`. `node.yaml` — машинно-локальная запись идентичности
и `store_id`; глобальная секция позволяет менять имя и роль, но не UUID.

- Уникальна только роль `server`: он один является целью runner `server`
  (раздел 9). `laptop` и `mobile` могут
  повторяться; узлы различаются по `name` (уникальный slug), и runner
  `laptop`/`mobile`/`here` резолвится в имя конкретного узла.
- Роль «клиент» (PWA) удалена: телефон — обычный узел роли `mobile`.
- `store_id` создаётся вместе с первой репликой и копируется на новую при
  bootstrap (раздел 10.4). Сопрячь два узла с разными непустыми store нельзя:
  это `SYNC_STORE_MISMATCH`, и человек выбирает, какую базу оставить. Слияние
  двух независимых баз в объём эпика не входит.

### 2.1 Узел mobile (TASK-432)

- Полная реплика store, пишет офлайн, задачи создаёт из своего запаса ID
  (раздел 6) и может сам быть runner (раздел 9).
- Только исходящие соединения: `serve` на телефоне не слушает сеть (кроме
  loopback), пиры к нему не подключаются, сопряжение инициирует телефон.
  Синк с телефоном идёт по инициативе телефона: pull, push и SSE-поток к
  пиру (10.5), либо через git-relay (10.6).
- Без systemd: синк-воркеры и sidecar tailscaled (11.5) живут внутри TUI или
  `kanban daemon`; при штатном выходе отправляется `bye` (10.3). Если Android
  убил процесс (phantom process killer), всё поднимается при следующем старте
  или тике.
- Отсутствие телефона — норма. Пиры показывают его нейтрально («Телефон: был
  в сети {ago}»), без кодов ошибок, предупреждений и `RUN_NODE_*` для задач, не
  запущенных на телефоне. Wake-on-LAN к mobile не применяется.

Реализация TASK-432: `serve`, TUI и daemon выбирают одного владельца исходящих
воркеров через локальный `sync/worker.lock`; `sync/serve.lock` даёт приоритет
запущенному serve. TUI/daemon уступают ему на следующем `sync.interval` без
ложного `bye`; после его выхода снова забирают worker lock. Остальные процессы
не дублируют синк. Владелец отправляет `hello` при старте и хвост журнала + `bye`
при штатном выходе (daemon также обрабатывает SIGINT/SIGTERM). Воркер телефона
делает pull/push/SSE к серверу; `POST /sync/ack {store_id, vector}` сообщает
серверу его вектор и store_id после bootstrap по исходящему соединению, без
обратного dial (для компакции и доверенного relay-пира).
Пиры не пробуют адрес outbound-узла ни при sync, ни при probe/notify.
Свежий входящий контакт показывает `ONLINE`; `bye` или отсутствие контакта
в течение трёх `sync.interval` показывает нейтральный `OFFLINE`.

## 3. Что реплицируется, а что машинно-локально

Правило по умолчанию: реплицируется всё, что описывает **доску**, и не
реплицируется всё, что описывает **процессы и пути этой машины**.

### Реплицируется

| Данные | Где лежит | Как сливается |
|---|---|---|
| Поля задач (кроме локальных ниже), включая `status`, `runner` | `tasks/<status>/TASK-N.md` | LWW по полю (5.2) |
| Создание и удаление задачи | — | create идемпотентен, delete оставляет tombstone (5.4) |
| Сообщения тредов | `threads/TASK-N.yaml` | объединение по uid сообщения, поля сообщения LWW (5.3) |
| Проект: `uid`, `id`, `name`, git-remote | `project.yaml` | LWW по полю |
| Конфиг проекта | `.kanban/config.yaml` | LWW по ключу (dotted path) |
| Глобальный конфиг, кроме локальных секций | `<store>/config.yaml` | LWW по ключу |
| Ролевые инструкции | `.kanban/instructions/<role>.md` | LWW по файлу |
| Картинки | `.kanban/assets/images/` | content-addressed blob (sha256), только добавление |
| Legacy-контекст | `.kanban/context/` | локальный; не входит в bootstrap и не реплицируется |
| Дескриптор запуска | `<store>/sync/meta/` | по ключу узла, пишет только runner (раздел 7) |
| UID задач и алиасы номеров | `<store>/sync/meta/uids.json` | раздел 6 |

### Машинно-локально (никогда не уходит на пир)

| Данные | Почему |
|---|---|
| `sessions/`, pid, heartbeat-файлы | процессы этой машины |
| `.lock`, `<store>/.lock`, `daemon.lock`, `pump.lock` | flock работает только в пределах одной машины |
| `worktrees/`, `backups/` | абсолютные пути и checkout этой машины |
| `project.yaml: work_path`, `migrated_from` | у каждого узла своя рабочая папка проекта |
| `logs/`, `detached/`, `provenance/`, `forms/` | артефакты локальных запусков. Отдаются по API только для чтения (раздел 11) |
| `stats/events.jsonl` | статистика узла. Отчёт строится по узлу |
| `recent_models`, `limits.json`, кэш лимитов | зависят от логинов этой машины |
| поля задачи `session`, `run_phase`, `crash_restarts`, `restart_at`, `auto_resumes` | локальная сессия, очередь и автоматика перезапуска. Наружу их заменяет дескриптор запуска |
| `rev` треда | локальный счётчик оптимистичной записи |
| `<store>/config.yaml`: секции `node`, `sync`, `serve`, `daemon`, `tui`, `net` | идентичность, пиры, сеть, интервалы, отображение |
| `<store>/sync/node.yaml`, `peers.yaml`, `tokens.yaml` | секреты, права 0600 |
| `sync/FORMAT`, заглушка `meta/state.json`, `meta/index.json`, `meta/since.json`, `sync/legacy-v1/` | версия этой машины, перестраиваемый кэш и перенесённые файлы v1 |
| `<store>/net/tailscale/` | state dir managed tailscaled (каталоги 0700, файлы 0600), раздел 11.5 |
| `sync.clone_root` и ленивые клоны в нём | пути этой машины, раздел 8 |

Реплицируемые настройки, которые ссылаются на локальные вещи (например,
`agents:` с путём к бинарю), применяются как есть. Если на узле бэкенда нет,
запуск падает с `RUNNER_BACKEND_MISSING`, а не с ошибкой синхронизации.

## 4. Журнал операций и HLC

### 4.1 HLC

Hybrid Logical Clock — это тройка `(wall_ms, counter, node_id)`, и сравнивается
она лексикографически. Правила:

- на локальной записи: `wall = max(now, last.wall)`. Если `wall` совпал с
  прошлым, то `counter + 1`, иначе `counter = 0`;
- на приёме чужой операции: `last = max(last, remote)`. Следующая локальная
  запись будет строго больше;
- последнее значение хранится в `<store>/sync/hlc` и переживает рестарт. После
  рестарта часы не уходят назад, даже если системные отстали;
- если чужой `wall_ms` опережает локальные часы больше чем на `sync.max_skew`
  (по умолчанию 5 мин), операции этого пира не применяются, а пир получает
  статус `SYNC_CLOCK_SKEW`. Иначе один узел с убежавшими часами выигрывал бы
  все LWW.

В JSON HLC записывается как `[wall_ms, counter, "node_id"]`.

### 4.2 Операция

Изменения ловятся на уровне `Storage` при атомарной записи как diff «до/после».
`core/operations.rs` при этом не меняется. Одна логическая запись — одна
операция:

```json
{"op": "6f1c…:1042",                 // (node_id, seq), seq монотонен на узле
 "hlc": [1760207776986, 3, "6f1c…"],
 "store": "2b9e…",
 "project": "<project uid>",
 "entity": "task",                    // task | message | project | config | instructions | blob | run | tombstone
 "id": "0b7e…",                       // UID задачи (раздел 6); для message — uid сообщения
 "set": {"status": "review", "updated_at": "…"},
 "prev": {"status": [1760207000000, 0, "a1b2…"]},   // HLC значения, которое перезаписали
 "actor": "agent"}                    // human | agent | kanban: роль автора записи
```

- `prev` нужен для обнаружения конфликтов (5.2).
- `actor` — для аудита. Правила колонок и agent/human проверяются на узле, где
  сделана запись, а при применении на пире повторно не проверяются: пиры
  доверяют друг другу после сопряжения.

### 4.3 Журнал и вектор версий

Формат store — 2 (`sync/FORMAT`, раздел 4.6). Свои и чужие узлы лежат одинаково.

- `<store>/sync/journal/<node_id>/<first_seq>.jsonl` — сегмент, `first_seq` —
  20 цифр. Одна операция на строку, seq строго непрерывны. Последний сегмент
  активный: батч дописывается одним `write_all` и `sync_data`. Неполная
  последняя строка обрезается до append. Когда файл достигает
  `sync.journal.segment_bytes` (по умолчанию 4 МиБ), он запечатывается и
  открывается следующий. Один батч может быть длиннее порога: ролл решается
  до записи, а не посередине батча.
- `<store>/sync/journal/<node_id>/ahead.jsonl` — операции с дырой
  (`seq > голова + 1`), дедуп по seq. Непрерывный префикс переносится в сегмент,
  когда дыра закрывается. В вектор и в `operations_after` эти строки не входят.
- Вектор версий — seq последней полной строки активного сегмента каждого узла,
  не ниже уже упрощённого `compacted`. Синк — это «пришли всё после моего
  вектора» по непрерывным сегментам.
- `sync/meta/index.json` — перестраиваемый кэш запечатанных сегментов: первый
  и последний seq, последний HLC, размер, смещения каждой 128-й операции. Это
  не источник истины. По нему нельзя пропускать активный сегмент: его `last`
  устаревает между записями. Битая строка — ошибка чтения, а не пропуск.
- `sync/meta/projection.json` — периодический снимок проекции: `format`,
  `through` (узел → seq, сегмент, смещение), поля с HLC, `lifecycle`,
  `compacted` и состояние прунинга. Пишется потоково (`serde_json::to_writer`
  во временный файл, fsync, rename, fsync каталога), не собирается строкой в
  памяти. Пороги `sync.journal.snapshot_ops` (1000) и `snapshot_secs` (300)
  считаются между процессами по `sync/meta/since.json`. Удаление проекции
  пересобирает её из сегментов, пока история не упрощена; после прунинга
  свёрнутые поля живут только в снимке. Процесс serve/TUI держит проекцию в
  памяти и узнаёт её по `change_token`; другой процесс по-прежнему читает файл.
- `sync/meta/uids.json` — `project_uids`, `message_uids`, `task_uids`,
  `task_aliases`. Файл переписывается, только когда карта изменилась.
- `sync/meta/conflicts.jsonl` — живые конфликты, каждый раз пересчитанные по
  удерживаемой истории. `conflicts-archive.jsonl` — конфликты, замороженные
  при прунинге (4.5).
- `sync/hlc` пишут приём чужой операции и `Journal::observe`. Локальная запись
  файл часов не трогает: следующее значение берётся как максимум файла, реплея
  и последней своей строки.
- `sync/meta/state.json` — заглушка для бинарников 0.8.0–0.8.2:
  `{"format":2,"vector":"store migrated to sync format 2; upgrade kanban4ai"}`.
  Старый захват не десериализует `vector` как карту и не портит seq. Это не
  состояние журнала.

`lifecycle` — карта `(project, сущность, id)` → `{created, claim, deleted,
restored}`. Все четыре поля коммутативны (min/max), поэтому порядок доставки
не важен. `created` — минимальный HLC любой операции, кроме tombstone и
restore; `claim` — самый ранний op задачи с `set.id = TASK-N`; `deleted` и
`restored` — максимальные HLC. Tombstone и restore ключуются по `set.entity`,
а поля LWW остаются на `op.entity`. Вектор в памяти двигается только на
непрерывном seq (`seq == vector[node] + 1`); после реплея он равен головам
сегментов.

`Journal::state` возвращает вектор, поля, lifecycle, карты UID и `compacted`.
`Journal::operations(Some(node))` — удерживаемые операции (`seq > compacted`,
включая `ahead`) по HLC; `None` — все узлы. Дескрипторы запусков по-прежнему
лежат в `sync/meta/` отдельно от фронтматтера задач.

### 4.4 Локальное ядро (TASK-406)

- Общая точка захвата — `storage::atomic_write_text`; `operations.rs` не
  меняется. Захватываются store-проекты (`projects/<id>/`): задачи, сообщения
  тредов, `project.yaml`, конфиг проекта, а также глобальный `config.yaml`.
  Доски старого in-place формата продолжают работать без sync-артефактов;
  после миграции в store их записи проходят через этот же захват.
- Одна запись задачи/проекта/конфига даёт одну операцию с изменёнными полями;
  запись треда даёт операции для изменённых сообщений. Удаление задачи через
  `Storage::delete_task` и исчезновение сообщения дают `tombstone`.
  Удалённый ключ в diff представлен JSON `null`; конфиги используют dotted
  paths. Смена status сравнивается со старым файлом в другой колонке, а не
  считается повторным созданием задачи.
- Дополнительно к `session` из задач исключены локальные поля изоляции:
  `worktree`, `branch`, `base_commit`, `integration`, `cleanup_retry_at`.
  У проекта не реплицируется локальная история `last_opened_at`.
- UID проектов и соответствие `MSG-NNN` → UID хранятся в
  `sync/meta/uids.json`. UID нового сообщения равен op_id создания,
  `parent_id` в операции — UID родителя. `rev` и UID не добавляются в YAML
  треда. Повторное использование display-id после удаления создаёт новый UID.
- `Journal::observe` проверяет переданный лимит skew и сохраняет принятый
  HLC; после рестарта следующая запись строго больше принятой операции.
- `sync/intent.json` — маленький redo одной локальной записи под board lock и
  `sync/.lock`. В нём путь, признак внешней правки, наблюдение drift, имя
  сегмента, `start_offset`, `through_seq` последней операции батча, дельта
  четырёх карт UID и признак проекции запуска. Дальше, в том же захвате:
  файл данных (для внешней правки файл не пишется; копии задачи в других
  колонках удаляются), один append своих операций, дельта UID, проекции
  запусков, drift. Затем intent удаляется и, по порогам 4.3, пишется проекция.
  `pending.json` и `sync/snapshot/` больше не используются.
- Обрыв: неполная последняя строка сегмента обрезается. Если голова своего
  узла уже не меньше `through_seq`, запись закоммичена — UID, проекции
  запусков и drift доприменяются один раз и не захватывают файл заново.
  Иначе сегмент обрезается до `start_offset`, а записанный файл сверяется
  через drift ровно одним op «изменено снаружи». Следующий seq без дыры и
  без дубля. Пока идёт это восстановление, повторный захват не открывает
  журнал рекурсивно.
- На запись нет чтения и перезаписи полного состояния. fsync получают intent,
  файл данных, одна порция журнала и, только при изменении, `uids.json`.
  Снимок проекции — по `snapshot_ops` / `snapshot_secs`, не на каждый op.

### 4.5 Прунинг

`Journal::prune(acks)` заменяет прежний `Journal::compact`. `acks` — карта
«участник → подтверждённый им вектор». Участники — ключи этой карты и все
чужие узлы локального вектора. Участник без вектора считается нулевым, поэтому
store, получавший операции от узла без подтверждения, ничего не теряет.
Участников нет вообще (только свои операции, пиров нет) — стабилен весь
локальный вектор, и журнал остаётся около одного активного сегмента.

Фронтир считается с лагом, чтобы опоздавшая конкурентная операция всё ещё
сравнивалась:

- `C` — поточечный минимум локального вектора и всех ack (нет ключа — 0);
- `R[N] = ack_N[N]`, иначе 0. Пара `(C, R)` запоминается как candidate/required;
- пока `local[N] < R[N]` хотя бы для одного участника, прунинг не двигается;
- когда локальный вектор покрывает `R`, стабильная граница
  `S = max(прежняя S, C)`.

Причинное замыкание `H ≤ S` — наибольший по-узловой префикс `S`, в котором у
каждой операции все `prev` попадают внутрь `H`. HLC узла монотонен по seq,
поэтому «h внутри H» значит `h` не больше HLC операции на seq `H[h.node]`
(или сохранённого HLC фронтира, если эта операция уже упрощена). Итерация идёт
до неподвижной точки по диапазону `(прежний compacted, S]`. Ни одна
удерживаемая операция не является потомком выброшенной: обход предков,
упёршийся в отсутствующую версию, честно даёт «не предок».

Действия одного `prune`:

1. Конфликт, у которого и победитель, и проигравший внутри `H`, переносится
   из `conflicts.jsonl` в `conflicts-archive.jsonl`. Архивная строка, у которой
   оба часа внутри `H` и wall победителя старше недели, удаляется. Живой файл
   пересчитывается по удерживаемым операциям; конфликт вне `H` остаётся живым.
2. Запечатанные сегменты с `last_seq ≤ H[node]` удаляются целиком. Активный
   сегмент не трогается. `compacted = H`. `operations()` не показывает строки
   с seq не больше `compacted`, даже если они ещё лежат в активном файле.
3. GC `sync/blobs/<hash>`: удаляется blob, на который не ссылаются
   `drift.jsonl`, поле `blob` сущности file, удерживаемые операции и
   `remote-pending.json`, и чей mtime старше часа. Моложе часа не трогается,
   чтобы не обогнать `PUT /sync/blobs` до прихода операций.
4. Сразу пишется `projection.json` и перестраивается `index.json`.

Вызовы: после записи ack в `settings::acknowledge` — векторы из
`sync/exchanges.yaml` по всем `sync.peers`, отсутствующий ack — пустой вектор
(serve-воркер, не под async-захватом sync lock). Relay после успешного push
запоминает опубликованный вектор в `sync/meta/relay-ack.json` и прунит с
участником `relay`, чтобы неопубликованное не исчезло (`SYNC_RELAY_GAP`).
Если в конфиге нет пиров и relay выключен, тот же прунинг выполняется вместе
со снимком проекции. Ошибка разбора конфига прунинг не включает и локальную
запись не роняет. Пока пиры есть, обычный снимок журнал не прунит.

`operations_after` с `after[node] < compacted[node]` (и `compacted > 0`)
возвращает `SYNC_SNAPSHOT_REQUIRED`: такой пир не участник прунинга и догоняет
базу снимком (10.4).

### 4.6 Версии формата и миграции

Константы: `STORE_FORMAT = 2`, `OP_FORMAT = 1`, `SYNC_PROTOCOL = 2`,
`MIN_SYNC_PROTOCOL = 1`.

- `sync/FORMAT` — текст `2\n`, точка коммита миграции. `Journal::open` читает
  его после восстановления bootstrap и до remote redo. Каталога `sync/` нет —
  открытие создаёт его, как раньше. Выключение журнала без пиров — отдельная
  задача: отсутствие участников уже держит журнал около одного сегмента (4.5).
- Формат новее бинарника: ошибка
  `SYNC_STORE_TOO_NEW: store format N, binary supports 2; upgrade kanban4ai`.
  Ничего не пишется, захват доски не выполняется.
- Формат старше: под store, board и sync lock идут упорядоченные миграции.
  Каждая идемпотентна и перезапускаема. `FORMAT` пишется атомарно только после
  успеха. Пустой store (нет v1 `meta/state.json` и нет `journal/`) сразу
  получает формат 2 и заглушку.
- У операции всегда есть `v` (`OP_FORMAT`) и словарь неизвестных полей. Новое
  поле — только optional со значением по умолчанию; оно сохраняется в сегменте
  и при пересылке. Смысловой разрыв формата — это `OP_FORMAT + 1`. Батч, в
  котором любая операция новее известной, целиком отвергается:
  `409 SYNC_OP_FORMAT_TOO_NEW`.
- File-op (`entity=file` и захват drift): `set = {path, blob, size}`. `size` —
  необязательное число. Байты в операцию не кладутся; blob уходит отдельно и
  только если у получателя его нет.
- Ответ `GET /sync/vector` несёт `protocol` и `min_protocol`. Нет поля — 0, это
  легаси и читается как протокол 1. Клиент шлёт заголовок
  `x-kanban-sync-protocol`. Диапазоны не пересекаются —
  `SYNC_PROTOCOL_MISMATCH`, обмена нет. Отправитель не шлёт операции с `v`
  выше максимума эффективного протокола (протокол 2 → `v ≤ 1`). У heartbeat
  relay то же поле `protocol` со значением по умолчанию.
- Снимок bootstrap несёт `format` (нет поля — 1). Формат новее бинарника —
  отказ до записи файлов. 1 ставит файлы v1, миграция на следующем open.
  2 ставит файлы v2; установщик затем пишет `FORMAT` и заглушку. Белый список
  путей принимает старый `sync/journal/<file>` для снимка v1 и
  `sync/journal/<node>/<file>.jsonl` (включая `ahead.jsonl`), плюс
  `meta/projection.json` и `meta/uids.json`. `index.json`, заглушка
  `state.json`, `since.json`, `relay-ack.json` и `FORMAT` в снимок не входят.

Миграция v1 → v2, под теми же блокировками, что восстановление bootstrap:

1. Довести старый redo: `remote-pending.json` v1, затем `pending.json` v1.
2. Прочитать v1-состояние с полем `operations` и плоские
   `journal/<node>.jsonl`, объединить по id операции.
3. По каждому узлу непрерывный префикс с seq 1 пишется сегментами в
   `sync/.staging/<node>/` (ролл по `segment_bytes`); остаток — в `ahead.jsonl`.
   `lifecycle` строится по всем операциям. Проекция получает поля, lifecycle,
   `through` и v1 `compacted`; карты UID копируются; `conflicts.jsonl` остаётся
   как был.
4. Атомарно пишется `FORMAT=2`. Это коммит.
5. Плоские журналы, старый `state.json` и `snapshot/` переносятся в
   машинно-локальный `sync/legacy-v1/` (не реплицируется, можно удалить
   руками). Каталоги staging становятся `journal/<node>/`. Пишется заглушка.

Сбой до шага 4 стирает частичные сегменты и новые meta-файлы и начинает
миграцию заново; v1-журналы и конфликты не удаляются. После `FORMAT` шаг 5
повторяется при каждом open, пока файлы v1 ещё на месте. Имя
`journal/<node>.jsonl` не может сосуществовать с каталогом `journal/<node>/`,
поэтому сегменты появляются в журнале только после переноса плоских файлов.


## 5. Слияние

Чужие операции применяет движок под board lock проекта. Применение
идемпотентно: операция с уже виденным `op` пропускается.

### 5.1 Единица слияния

Единица слияния — поле. Правка `title` на одном узле и `status` на другом в
конфликт не попадают: применяются обе.

### 5.2 LWW по полю и конфликт

Для каждого поля хранится HLC последней записи. Входящая операция по полю `f`:

1. `meta[f].hlc == op.prev[f]`: обычная перезапись, конфликта нет.
2. `meta[f].hlc > op.prev[f]` и `meta[f].hlc != op.hlc`: записи
   **конкурентные**, обе стороны меняли поле, не видя друг друга. Побеждает
   больший HLC, при равенстве `wall_ms` и `counter` — больший `node_id`.
   Проигравшее значение сохраняется:
   - запись в `<store>/sync/meta/conflicts.jsonl` (проект, задача, поле, оба
     значения, оба HLC, узлы);
   - board note в треде задачи от `kanban`: «Конфликт поля «{field}»: оставлено
     значение с {winner_node} ({winner_time}), на {loser_node} было: {loser_value}».
   Это правило симметрично: оба узла фиксируют один и тот же конфликт с одним
   победителем. Проигравший `X` не образует новую пару с правкой `Z`, если
   `Z.prev[f]` новее `X`: `Z` написана поверх версии, которая уже победила
   `X` (или поверх версии с её значением), и этот конфликт уже записан один
   раз. Иначе каждая следующая правка победителя писала бы новую note.
   Предки поля проверяются по интервалам обхода леса `prev` за O(1); пары
   перебираются только среди конкурентных версий.
3. `op.hlc < meta[f].hlc` без конкурентности: значение устарело и молча
   игнорируется.

Конфликт снимается кнопкой «Взять другую версию» (TASK-416). Это обычная новая
запись с новым HLC, и она расходится по узлам как любая другая. Черновик
ответа `draft` сливается по LWW и конфликтов не создаёт.

Реализация TASK-416: шапка доски и деталей показывает подтверждённый обмен,
очередь по peer vector и код доступности; пробы выполняются в фоне. Карточка
помечает активные конфликты полей задачи и её сообщений бейджем `⚠ sync`.
В деталях `Ctrl+←/→` выбирает конфликт, кнопка «Взять другую версию» или
`Ctrl+V` записывает проигравшее значение с новым локальным HLC и `actor: human`.
Если поле уже изменилось, выбор отклоняется. История в `conflicts.jsonl` и
board notes сохраняется; UI показывает конфликт только пока текущее поле
ещё имеет HLC победителя. Без пиров новая шапка не занимает строку.

### 5.3 Треды

- Сообщение идентифицируется глобальным **uid** = op_id операции, которая его
  создала. По uid треды и объединяются (расширение существующего
  `merge_threads` по id). Сообщения только добавляются. Изменяемые поля
  сообщения (`status`, `answer`, `answered_by_role`, `draft`, `body` у
  review-edit) сливаются по 5.2.
- **Отображаемый `MSG-NNN` может совпасть.** Номер выдаётся как `max + 1` по
  треду, поэтому два узла офлайн создадут два разных `MSG-053`. При слиянии
  номер оставляет сообщение с меньшим `(hlc, node_id)`, а второе
  детерминированно получает суффикс стабильного `node_id`: `MSG-053@6f1c…`.
  Имя (`laptop`/`server`) можно подставлять при отображении, не меняя идентичности.
  `parent_id` хранится в операциях как uid, поэтому ссылки на переименованное сообщение
  не ломаются. Новые номера продолжаются с `max(числовая часть) + 1`.
- Порядок сообщений в файле треда — по HLC создания.
- Компакция контекста (rule-based) выполняется на одном узле и реплицируется
  как операции: tombstones удалённых сообщений плюс новое сводное сообщение.
  На другом узле компакция того же треда не запускается повторно, пока не
  применены её операции. Порог считается по реплицированному состоянию.

### 5.4 Создание, удаление, tombstones

- Создание задачи или проекта идемпотентно по ID/uid. Повторная доставка
  ничего не меняет.
- Удаление — это операция `tombstone` с HLC. Tombstone побеждает любые
  правки поля с меньшим HLC. Правка с большим HLC, сделанная конкурентно
  (на другом узле не видели удаления), удаление **не** отменяет: удаление
  выигрывает, правка уходит в список конфликтов, и задачу можно восстановить
  кнопкой. Восстановление — явная операция `restore`.
- Часы удаления и восстановления остаются в `lifecycle` и после прунинга
  операций (4.5). Номер удалённой задачи больше
  никогда не выдаётся (раздел 6). Создание задачи идемпотентно по UID; две
  задачи с одним `TASK-N` с разных узлов — разные задачи (раздел 6).
- Проекты: если два узла офлайн зарегистрировали разные проекты с одним slug
  `id` (разные `uid`), проект с большим `(hlc, node_id)` получает следующий
  свободный суффикс `-2`, `-3`… по существующему правилу коллизий.
  `work_path` у каждого узла свой (раздел 3). Если на узле рабочей папки нет,
  проект показывается так же, как сейчас показывается отсутствующая папка.

### 5.5 Перемещение файлов

`status` — обычное поле. Директория `tasks/<status>/` выводится из него: движок
применения переносит файл атомарно под board lock тем же путём, что и
`move_task`, но без проверки правил (они проверены на исходном узле).
Побочные эффекты колонок (auto-launch chained, resume_after_last_answer,
уведомления) срабатывают **только на runner-узле задачи**: на нём, если
запуск есть, иначе на узле, где сделана запись. Иначе каждый реплицированный
переход запускал бы агентов на обоих узлах.

### 5.6 Движок применения (TASK-407)

- `Journal::apply_remote(ops, max_skew_ms)` принимает доверенные операции одной
  базы; лимит skew передаётся из настроек вызывающим кодом. Проверки store,
  идентичности op/node, путей и локальных полей выполняются до изменения данных.
  Транспорт (10.5) вызывает его для `POST /sync/ops` и потока SSE.
- Движок держит store lock, затем board locks в порядке путей, затем sync lock.
  Новый destination при коллизии проекта блокируется без удержания sync lock;
  старые board locks остаются удержанными. Правила автора и колонок повторно не
  вызываются, агентские запуски и уведомления здесь не выполняются.
- Сравнивается полная тройка HLC. История для `prev` — удерживаемые операции
  (`seq > compacted`, включая `ahead`) плюс входящий батч, а не полный
  `state.json`. Проверяется вся цепочка предков поля, а не только текущий
  победитель: иначе доставка третьей конкурентной ветки или пропущенного предка
  меняла бы список конфликтов. Конфликты нормализуются по паре версий; JSONL и
  board notes являются детерминированной проекцией этой истории. `draft`
  выигрывает по LWW без записи конфликта. Против уже упрощённой истории правка
  после удаления видна по `lifecycle.deleted`: HLC правки больше удаления и
  нет более нового `restored`.
- Дедуп входящей операции: seq не больше головы узла, seq уже есть в `ahead`,
  или seq не больше `compacted`. Принятые операции обновляют поля и lifecycle
  сразу, в том числе пока в seq дыра; вектор двигается только на непрерывном
  seq. Применение не порождает локальных ops. Доставка вне порядка остаётся
  обязательной.
- `sync/remote-pending.json` — redo принятого батча: доски, изменённые файлы,
  blobs, только эти операции, карты UID, текст конфликтов и HLC. В него не
  входят `meta/state.json` и журналы. Файл, чьи байты совпали с новыми, и
  удаление отсутствующего файла пропускаются. Порядок: записать redo, дописать
  операции в сегменты (с `ahead`), записать файлы и метаданные, удалить redo,
  снимок проекции по порогам. Повторное открытие дописывает недостающие seq
  один раз. Запись рабочих файлов обходит локальный capture. Локальные поля
  существующей задачи, конфигов и проекта сохраняются. v1 `remote-pending.json`
  доводится миграцией до нового восстановления. Повторное применение в том же
  процессе проецирует только сущности входящего батча; холодный старт, смена
  псевдонима проекта и перенумерация по-прежнему проецируют доску целиком.
- До получения обязательных полей создания дельты остаются в метаданных:
  неполный task/project не публикуется. Новый проект имеет пустой локальный
  `work_path` и отображается как проект без рабочей папки. Разные UID с одним
  slug сортируются по HLC создания; суффиксы не занимают исходные slug других
  известных проектов.
- Сообщения строятся по UID и объединяются существующим `merge_threads` по
  display-id после назначения детерминированных алиасов. В коллизиях суффикс
  содержит стабильный `node_id`: wire op не содержит имя узла, а локальное имя
  нельзя использовать для сходящейся проекции. Ссылки на родителей переводятся
  из UID после полного назначения алиасов. Числовая часть `MSG-NNN@node_id`
  учитывается при выдаче следующего номера. `rev` увеличивается при изменении
  сообщений, но остаётся машинно-локальным и не входит в свойство сходимости.
- Tombstone удерживает удаление независимо от более нового edit; edit сохраняется
  в конфликте. Явный `restore` с HLC выше tombstone восстанавливает сохранённые
  значения. Часы создания, заявленный номер и часы удаления живут в lifecycle
  и переживают прунинг операций (4.5).
- `tests/sync_apply_test.rs` перебирает все 720 порядков доставки создания,
  трёх конкурентных веток и причинного продолжения, а также все перестановки
  сценариев сообщений, удалений и коллизий проектов. Проверяются поля, clocks,
  конфликты и сообщения (без локального `rev`), повторная доставка, сохранность
  локальных полей, stale writer и завершение redo.


## 6. Номера задач: локальная выдача и перенумерация (TASK-510)

Номер задачи всегда выдаётся локально и без сети, на любом узле, в любой
роли, с сервером или без него, сопряжённом или нет:
`Storage::get_next_id` = `max(номера живых файлов, исторические номера
проекта) + 1` под board lock. Исторические — все номера из реплицированного
состояния: заявленные задачами (включая удалённые и ещё не показанные на этом
узле), tombstones, текущие и ретированные отображаемые номера. Номер не
переиспользуется и после компакции. Аренд, блоков, выдающего узла и
`SYNC_ID_BLOCK_EXHAUSTED` больше нет.

- **Идентичность.** Внутренний ключ задачи — UUID (`id` операций `task`,
  `run` и `tombstone`, `task_id` сообщений). `TASK-N` — отображаемое имя:
  фронтматтер `id`, имя файла, имя треда. Захват (`sync::capture`) выдаёт UUID
  новой задаче и хранит соответствие `(project, "task", TASK-N) → UID` в
  `meta/state.json` (`task_uids`). Операция создания несёт заявленный номер в
  поле `id`. Ссылки `parent_task`, `chained_to`, `depends_on` реплицируются
  как UID и при проекции снова становятся текущими `TASK-N`.
- **Совместимость.** Задачи, захваченные до 0.8, имеют `id = TASK-N` в
  операциях; такой UID — сам номер. Неизвестный UID везде трактуется как
  отображаемый номер, поэтому старые журналы, дескрипторы запусков и
  треды продолжают работать. Операции `entity: lease` из старых журналов
  принимаются и игнорируются. Узлы до 0.8.x с этой схемой не совместимы
  (они показали бы UUID как имя файла): обновлять все узлы store вместе.
- **Коллизия.** Два узла офлайн создали один `TASK-N` — это две задачи с
  разными UID. При каждой проекции (`apply_remote`) номера выводятся заново
  как чистая функция реплицированных операций, поэтому все узлы приходят к
  одному результату при любом порядке доставки:
  1. Задачи проекта сортируются по `(HLC первой операции, UID)`; HLC включает
     `node_id`, так что раньше HLC, затем `node_id`.
  2. Первая задача с данным номером сохраняет его.
  3. Остальные по тому же порядку получают следующий номер выше своего,
     который никто не заявлял и который ещё не выдан при перенумерации.
  Перенумерация не меняет UID: правки, сообщения, запуски и ссылки других
  задач остаются привязаны к той же задаче. Позднее пришедшая заявка на тот
  же новый номер снова разрешается этим правилом.
- **Алиасы.** Ретированный номер (заявленный и ранее показанный на этом
  узле) сохраняется в `task_aliases` как `старый TASK-N → UID`.
  `Operations::get_task` и все CLI-команды с `<id>` резолвят старый номер в
  новый, если он больше не называет живую задачу, а для агентской сессии
  (`KANBAN_SESSION`), привязанной к перенумерованной задаче, — всегда.
- **Что переезжает на проигравшем узле** (одной redo-транзакцией проекции):
  файл задачи, тред `threads/TASK-N.yaml` (с локальными ключами `MSG-NNN`),
  `task_id` локальных сессий, ссылки во фронтматтере других задач.
  Локальные поля `worktree`, `branch`, `base_commit` остаются на задаче:
  перенумерованная задача продолжает работать в своей
  `worktrees/TASK-<старый>` и ветке `kanban/TASK-<старый>` по записанным
  полям. GC worktree считает живыми имена, записанные на задачах; новая
  задача, чей номер уже занят чужим worktree или веткой, получает
  `TASK-N-<время>`.
- Текст описаний и сообщений с упоминаниями `TASK-N` не переписывается.
- Сообщения тредов номера не выдают (5.3).

## 7. Запуски: локальное состояние против дескриптора

Сессия, pid, heartbeat, worktree и `task.session` остаются на runner-узле.
Наружу реплицируется **дескриптор запуска**, по одному на узел:

```yaml
# <store>/sync/meta/<project>/runs/TASK-405.yaml
runs:
  6f1c…-uuid4:                  # стабильный node_id; запись делает только этот узел
    node_id: 6f1c…-uuid4
    name: server               # имя для отображения; переименование не меняет ключ
    role: server
    gen: 3                      # поколение: max(gen всех ключей) + 1 при новом запуске/очереди
    state: running              # queued | running | waiting | finished | failed
    phase: executor
    started_at: …
    branch: kanban/TASK-405
    heartbeat: …                # прорежен: не чаще раза в sync.run_heartbeat (60 с)
    code: null                  # код падения из раздела 13.2
```

- Каждый узел пишет только свой ключ, поэтому конфликтов по дескриптору нет.
- Пир показывает «выполняется на сервере» и **не** делает reap или
  crash-detect чужих сессий. Падение runner-узла пир видит через статус узла
  (раздел 12) и проставляет коды `RUN_NODE_*` от имени `kanban` в треде, но
  сам дескриптор не меняет.
- Очередь, слоты и лимиты конкурентности — на runner-узле.
- **Защита от двойного запуска онлайн.** Запуск всегда выполняет сам
  runner-узел (локально или через `POST …/launch`). Перед стартом он проверяет
  дескрипторы: если у другого узла `running/waiting/queued` и тот узел в сети,
  запуск отклоняется с `RUN_ALREADY_RUNNING`.
- **Двойной запуск при разрыве** не предотвращается (узлы не видят друг
  друга), а обнаруживается после слияния: в дескрипторе два ключа с
  одинаковым `gen`. Подробности в сценарии 14.3.
- **Управление с любого узла (TASK-436).** `stop`, `answer` и `rerun` на
  задаче, которая выполняется на другом узле, — обычные операции журнала
  (`stop` и `rerun` — `entity: run`, уникальный `id = op_id`,
  `set.command = {task, node, generation, action}`; `answer` — правка сообщения
  треда). Они доходят до runner любым транспортом, включая git-relay;
  runner применяет их после durable apply вне sync/board locks. Команда другого
  поколения игнорируется, локальные receipts исключают повторное исполнение.
  HTTP stop/rerun на чужом узле также записывает intent, а не прямой proxy.
- **Лог запуска с другого узла.** При прямом канале (LAN/tailnet) — live-follow
  `GET …/log?follow=1`. Иначе runner публикует хвост лога в
  `refs/kanban/logs/<node UUID>/<project UID>/TASK-N` (ограниченный размер,
  перезаписывается) через git-relay (10.6), и пир показывает возраст снимка.
  UID проекта обязателен: номера задач уникальны только внутри проекта.
- **«Продолжить на узле» (TASK-437).** Перенос работы между узлами: текущий
  runner коммитит WIP worktree в `refs/kanban/wip/TASK-N` и пушит в remote
  (или передаёт bundle), закрывает сессию с `finished`. Целевой узел создаёт
  worktree от этого WIP и запускает новую сессию с контекстом треда; `gen`
  растёт, двойного запуска нет. Если runner недоступен, перенос возможен
  только с последнего опубликованного WIP с предупреждением о потере
  неопубликованного.

### 7.1 Локальный API дескрипторов (TASK-409)

- `core/sync/run.rs` захватывает записи локальных session-файлов и изменения
  задачи через общий atomic writer. Session-файл сохраняется только локально;
  в тот же durable redo добавляется `entity: run`, `id = TASK-NNN`,
  `set = {node_id: descriptor}`. Ключ — UUID, а не изменяемое имя узла.
- Дескриптор целиком LWW внутри ключа runner; при приёме проверяются совпадение
  ключа, `node_id` и HLC-узла, формат и отсутствие неизвестных полей. Чужой узел
  не может записать другой ключ. Проекция YAML лежит в
  `sync/meta/<project-uid>/runs/TASK-NNN.yaml`; значения и clocks входят в
  `state.json` и compacted snapshot.
- Очередь публикует `queued` с `started_at: null`, переход к сессии сохраняет
  поколение и заполняет время старта. Отмена очереди/закрытие сессии публикуют
  `finished`, объявленное ожидание — `waiting`, локальный crash — `failed`.
  Поздняя запись старой сессии не завершает заменивший её запуск.
- `sync.run_heartbeat` в локальном глобальном конфиге — положительное целое
  число секунд, по умолчанию 60. Более частые heartbeat обновляют только
  session-файл. Изменения состояния/фазы/ветки публикуются сразу, не ожидая
  интервала heartbeat. PID, session ID, wait note/deadline, worktree и flock
  никогда не входят в run-операцию.
- `Journal::runs(project_alias, task_id)` возвращает все runner-дескрипторы;
  `remote_runs(board, task_id)` — только чужие активные. TUI-карточка, detail
  и `show` показывают `running/queued/waiting on <name>`. Чужому запуску не
  назначается локальный heartbeat-deadline и не создаётся session-файл.
  Автоматические queue dispatch, crash-restart и wake после ответа не
  подхватывают задачу с чужим активным дескриптором.
- `core/sync/control.rs` будит только владельца последнего запуска после
  синхронизации последнего открытого вопроса. Сохраняются `auto_launch.enabled`,
  `resume_after_last_answer`, slots и живой `ask --wait`; несколько ответов
  одной пачки будят один раз. Более поздний stop того же поколения не отменяется
  старым ответом. Ответ с другого узла не создаёт там сессию даже после
  `finished` последнего чужого запуска: wake остаётся у владельца последнего
  поколения. Перед wake/rerun закрепляется фактический runner, в том числе
  для запуска, созданного до pairing. На сервере нужны и `serve`, и `daemon`.
- Лог API возвращает `{text, at_ms, node_id, project, task, generation}`:
  UTF-8 хвост до `sync.log_tail_bytes` (default 65536; 1…1048576).
  `follow=1` — SSE `log` с полным ограниченным снимком при изменении,
  keepalive 15 с, `end` при закрытии/смене сессии. Права токена обязательны;
  symlink/special files не читаются, известные session ID и локальные пути
  маскируются. Это не очистка произвольных секретов, напечатанных backend.
- Relay публикует хвост раз в `sync.log_interval` (default 60 с), независимо
  от `relay_interval`; log ref — root commit без цепочки истории с
  force-with-lease только собственного ref. `relay_encrypt` применяет age
  и к логам. Снимок проверяется по сопряжённому узлу, store, проекту, задаче
  и поколению; локальный cache — `sync/logs/<node>/<project UID>/TASK-N.json`.
  TUI `L` открывает лог чужого/завершённого запуска: direct snapshot polling
  раз в секунду без блокировки UI, при отсутствии direct — relay cache с
  возрастом. `q` возвращает в исходный экран.
- Проверка доступности узла, онлайн-защита `RUN_ALREADY_RUNNING` и
  `POST …/launch` используют транспорт и статус пиров. Обычный локальный crash
  имеет `code: null`; диагностированный отказ backend/repository получает код.
  Пир не меняет descriptor при потере связи.

### 7.2 Ошибки runner (TASK-421)

- Реплицируемое поле задачи `run_failure` содержит `RUN_NODE_POWERED_OFF`,
  `RUN_NODE_UNREACHABLE`, `RUNNER_BACKEND_MISSING` или `RUNNER_REPO_MISSING`.
  Пока ошибок нет, поле отсутствует: legacy-файлы не меняются. `show` и API
  возвращают код; в треде остаётся сообщение от `kanban` с причиной и
  предложением перезапустить на другом узле.
- Sync-воркер и явный probe отмечают только задачи с активным дескриптором
  пострадавшего узла. `bye shutdown/sleep` даёт время объявления; без `bye`
  нужен пропавший run-heartbeat старше
  `3 × max(sync.interval, sync.run_heartbeat)`. Отсутствие LAN-пути само по себе
  не означает падение. Offline mobile получает код только для своих запусков.
- Сообщение включает UUID узла и поколение запуска; повторные проверки не
  засоряют тред. Чужая session не создаётся и чужой descriptor не переписывается.
  Возвращение связи без свежего heartbeat не снимает ошибку; свежий heartbeat
  либо закрытие того же запуска снимает текущий `RUN_NODE_*`, сохраняя историю.
- Перед запуском проверяется исполнимость backend (в том числе абсолютного
  пути). Ошибки входа из error-событий Claude/Codex/omp и ранней диагностики CLI
  получают `RUNNER_BACKEND_MISSING`, без слепого auth-retry. Отсутствующий
  рабочий каталог/неудавшаяся подготовка клона получает `RUNNER_REPO_MISSING`;
  отдельный контракт mobile `SYNC_NO_REMOTE` сохраняется.
- На вернувшемся runner локальный session reap и crash-restart продолжают
  использовать существующие настройки очереди, backoff и бюджета попыток.
  Пир не начинает чужую задачу автоматически: предложение другого узла
  требует явного запуска. Новый локальный запуск очищает текущий код.

### 7.3 Продолжить на другом узле (TASK-437)

- `kanban continue TASK-N --node <имя>` и `Ctrl+W` на Board/Detail выбирают
  конкретный сопряжённый узел. Диалог явно сообщает: живая сессия не переносится,
  запускается новая сессия с контекстом треда.
- Sync-воркер сохраняет dirty tracked и untracked файлы активного изолированного
  worktree раз в `sync.run_heartbeat`; нормальный выход TUI/daemon/serve и
  `serve --bye shutdown|sleep` принудительно сохраняют последний WIP.
  Нужен git remote проекта. Коммиты машинно-авторские, не требуют настроенной
  пользовательской Git identity; HEAD, пользовательский index и checkout не меняются.
- Публикуются `refs/kanban/wip/TASK-N` и отдельный checkpoint источника
  `refs/kanban/wip-runs/TASK-N/<gen>/<node UUID>`; оба namespace входят в
  code bundle/fetch. Локальная отметка успешной публикации —
  `.kanban/wip/TASK-N.published`, не реплицируется.
- `POST /api/v1/projects/<p>/tasks/<t>/continue` принимает
  `{runner: "<имя>", generation: <gen>, last_published: false}`.
  Устаревшее поколение даёт `RUN_ALREADY_RUNNING`, несколько активных
  источников — `RUN_DUPLICATE`. Онлайн-источник публикует WIP, закрывает session,
  останавливает tmux либо проверенную по PID/start-time background process group,
  затем публикует окончательный WIP и отпускает runner.
  Непроверяемый legacy background-процесс даёт `RUN_STOP_UNSUPPORTED`:
  handoff не запускает второй агент вместо безопасной остановки первого.
- Реплицируемый `continue_from` хранит SHA checkpoint, `runner` — новое
  закрепление. Цель создаёт отдельные ветку/worktree от checkpoint; старый
  checkout сохранён, каноническая ветка источника переименована в retained-ветку.
  Поколение растёт. Outbound-only mobile забирает durable launch-intent
  через sync и запускает его через daemon/TUI даже при `queue_enabled: false`.
  Двойные результаты после разделения сети сохраняются для Review (§14.3).
- Недоступный источник без подтверждения даёт `WIP_SOURCE_UNAVAILABLE`.
  `--last-published` либо отдельное подтверждение TUI разрешает использовать
  последний checkpoint именно исходного поколения/узла. Предупреждение:
  неопубликованные изменения не перенесутся, недоступная старая сессия не
  остановлена; её результат не выбрасывается при последующем слиянии.


## 8. Код: git между узлами

- **Синхронизируемый проект обязан иметь git remote.** Без remote проект
  синкается как доска, но запуск на mobile отказывает с `SYNC_NO_REMOTE`;
  между laptop и server остаётся `git bundle` по `serve` (`/git/…`, раздел 11).
- Клон проекта на пире создаётся лениво: при первом запуске на этом узле, в
  `sync.clone_root` (машинно-локально, по умолчанию `<store>/clones/`), и
  дальше обновляется автоматически. На телефоне кнопка **«Подготовить к
  поездке»** заранее клонирует/обновляет все проекты с runner, допускающим
  mobile, чтобы запуск офлайн не упёрся в `RUNNER_REPO_MISSING`. ssh-ключи
  для bundle не нужны; для remote используются учётные данные git этой машины.
- Ветки `kanban/TASK-N` после запуска пушатся в remote (и/или передаются
  bundle). Автопуша в `main`/рабочую ветку нет: landing — существующий механизм
  на узле с рабочей папкой.
- Перед запуском на другом узле live-снапшот рабочей папки, включая
  незакоммиченную работу (`commit-tree`), передаётся как
  `refs/kanban/integration`. Тогда `seed: live` на runner-узле видит то, что
  есть у человека на ноуте.
- После завершения запуска ветка `kanban/TASK-N` передаётся на пиры, и код
  физически оказывается на всех узлах. Landing в рабочую папку каждого узла
  выполняется существующим механизмом. Если не получилось, бейдж «ожидает
  landing на {node}».
- Ветка из запуска на «чужом» узле при двойном запуске называется
  `kanban/TASK-N@<node>`.

### 8.1 Передача кода (TASK-418)

- `core/code.rs` хранит ленивые машинные клоны в `sync.clone_root/<project-id>`.
  `git_remote` записывается в `project.yaml` при регистрации и перед передачей
  кода; путь клона остаётся локальным `work_path`. Создание выполняется во
  временном соседнем каталоге с rename только после успешного git clone/import.
- Проксирование `POST /api/v1/projects/<project>/tasks/<task>/launch` сначала
  публикует live-снапшот и подготавливает код на runner, затем запускает задачу.
  При наличии remote публикуются только `refs/kanban/integration` и ветки
  `kanban/*`; main и рабочая ветка человека не пушатся.
- `GET /git/<project>/bundle?have=<oid,oid,...>` возвращает git bundle.
  `have` — известные commit OID (SHA-1 или SHA-256), а не git rev expressions.
  Bundle включает HEAD, ветки и integration; первая передача полная,
  последующие могут исключать известную историю.
  HTTP читает/пишет bundle потоково через временный файл: размер репозитория
  не требует целиком держать bundle в памяти serve или прокси.
- `POST /git/<project>/bundle` принимает bundle. Непустое тело разрешено
  только по LAN/loopback, не по tailnet. Пустое тело с `?remote=<url>`
  подготавливает/обновляет клон через remote и допускается по tailnet.
  Оба метода требуют node bearer token. На mobile отсутствие remote —
  `SYNC_NO_REMOTE`.
- Обновление существующего клона не делает checkout/reset: bundle импортирует
  только `refs/heads/kanban/TASK-*` и `refs/kanban/integration`, remote fetch
  сохраняет обычные ветки в remote-tracking refs, а `kanban/*` — в локальные
  task refs. HEAD, index и правки рабочей папки не меняются. Уже подготовленный
  клон при запуске используется без повторного fetch (в том числе офлайн);
  refresh выполняется входящей передачей или предварительной подготовкой.
- В машинном клоне `seed: live` использует полученную integration напрямую;
  сборка нового снимка из старого checkout и GC re-baseline не затирают WIP
  исходного узла. Новая ветка задачи в таком клоне публикуется в remote;
  ошибка публикации записывается в тред как `Code publication pending`.
- `GET /git/<project>/status` возвращает `{project, state, path, remote,
  integration}`; `state` — `missing` или `ready`. Это API статуса клона для
  вкладки Sync; путь и наличие клона относятся к отвечающему узлу.

### 8.2 Завершённые ветки и landing (TASK-422)

- Перед landing/cleanup завершённого запуска коммитятся оставшиеся правки
  изолированного checkout. Commit OID (`tip`) и HLC старта (`start_hlc`)
  входят в переносимый дескриптор; машинный путь checkout не передаётся.
- Результат удерживается отдельным ref
  `refs/kanban/runs/<task>/<gen>/<node_id>`. Эти refs передаются через git remote
  без force: офлайн-запуск другого узла не может перезаписать результат.
  После успешной передачи публикуются Review-ветки `kanban/TASK-N`.
  `main`, рабочая ветка, HEAD и index пользователя не меняются.
- Завершение запуска пробует доставку сразу; embedded sync в TUI/daemon/serve
  повторяет её по `sync.interval`, в том числе без доступного HTTP-пира.
  `serve --sync` также выполняет доставку. Ошибка remote сохраняет результат
  локально и записывает `Code publication pending` в тред.
- Получатель импортирует только конкретные refs результатов, не заменяя свой
  integration ref. При отсутствии репозитория используется ленивый клон G01.
  В Review один результат автоматически проходит существующие
  `snapshot → preflight → materialize`; `land: manual` оставляет его ожидающим.
  Конфликт не пишет маркеры в рабочую папку получателя и не меняет её файлы.
- Каждый узел независимо пишет `landing:<node_id>` в metadata запуска:
  имя, поколение, выбранный tip и `pending`. Это отдельные owner-only LWW-поля,
  не перезаписывающие дескриптор runner. Подтверждения реплицируются;
  карточка показывает «ожидает landing на laptop» также на сервере, когда
  ноут сообщил о неудаче. `landing_pending` и `run_duplicate` в task-файле —
  только локальная проекция, не источник репликации.
- Два дескриптора одного поколения дают `RUN_DUPLICATE` на карточке и запись
  в треде. Без суффикса остаётся результат с меньшим `(start_hlc, node_id)`;
  остальные — `kanban/TASK-N@<node>`. При одинаковых именах узлов suffix
  включает `node_id`. Завершённый checkout проигравшего запуска переименовывается,
  живой checkout никогда не переставляется на чужой tip.
- Если первый executor уже синхронизировал Review, второй активный локальный
  executor всё равно может завершить свой результат того же поколения.
  Проверки владельца session и её Active-состояния остаются обязательными;
  новый автоматический bot-review при дубликате не запускается.
- При дубликате автоматический landing отключён. В Review человек выбирает
  `kanban integrate TASK-N --branch kanban/TASK-N@laptop` (или каноническую
  ветку) отдельно на каждом узле. Выбор не удаляет другую ветку; отдельные
  refs результатов продолжают удерживать оба commit OID.
- Проверки: `tests/code_landing_test.rs` — незакоммиченный результат после
  cleanup, неизменность HEAD/index и человеческих файлов, конфликт ноутбука
  с реплицируемым pending, сохранение обоих результатов при переходе первого
  узла в Review до завершения второго, ручной выбор, недоступный remote с
  доставкой после восстановления.


## 9. Runner

- `runner: server | laptop | mobile | here | auto` на трёх уровнях: глобально
  (`runner.default`, реплицируется), в проекте (`inherit | server | laptop |
  mobile | here | auto` через новую
  `InheritGroup::Placement` в `core/config.rs`), в задаче (поле `runner`,
  `inherit` по умолчанию). Без пиров runner игнорируется, и запуск идёт
  локально.
- `here` — узел, на котором нажали запуск. `auto` — первый доступный узел по
  `runner.auto_order` (по умолчанию `[server, here]`): есть сервер — запуск там,
  нет — у себя. Без вопросов, на телефоне тоже запускается молча.
- В момент старта `auto`/`here` резолвится в имя конкретного узла, и оно
  пишется в задачу (`runner: <name>`) и дескриптор. Повторные запуски и
  crash-restart идут туда же, пока человек не сменит runner.
- Явный `server` при недоступности сервера ставит задачу в очередь «ждёт
  server» (запуск уйдёт на сервер, когда он появится), если запуск
  автоматический (chain, очередь, crash-restart, ответ на вопрос). На телефон
  такой запуск не переезжает.
- UI выбора: **Auto / Сервер / Это устройство** (`laptop`/`mobile` доступны в
  настройках проекта и задачи).
- Колбэки агента (`$KANBAN_CMD`) пишут в реплику runner-узла, а синк разносит
  изменения дальше. Ноут можно выключить посреди задачи.
- **Подсказки появляются только при запуске и только при явном выборе узла.**
  `auto` диалог не показывает никогда. Если явно выбранный runner
  недоступен, вместо ошибки открывается диалог (TUI и тот же ответ API,
  TASK-420): код и текст причины (раздел 13) и кнопки
  `[Запустить на {другой узел}] [Ждать {узел} в очереди] [Разбудить сервер]* [Отмена]`.
  `*` — только если недоступен узел с `wol` (раздел 12.3). Других
  всплывающих подсказок нет.

### 9.1 Настройка размещения (TASK-417)

- Настройки и репликация реализованы в TASK-417; маршрутизация запуска —
  в TASK-419 (9.2). `Runner` отделён от роли узла `NodeRole`: `here` и
  `auto` — предпочтения, а имя узла — закреплённое место выполнения.
- Глобальный и проектный YAML: `runner.default` (по умолчанию `auto`) и
  `runner.auto_order` (по умолчанию `[server, here]`). В проекте
  `inherit.placement: true` наследует всю секцию `runner`.
- Поле задачи `runner` хранит явное предпочтение; отсутствие/null наследует
  проект. Возврат к inherit удаляет поле. Приоритет: задача → проект → global.
- Global Settings: **Auto / Сервер / Это устройство**. Project Settings и
  создание/редактирование задачи также предлагают Laptop/Mobile. Переключение —
  Left/Right или Space. `auto_order` настраивается в YAML.

### 9.2 Запуск на runner-узле (TASK-419)

- `Operations::start_task`, delegated take, chain и queue используют общий
  runner-dispatch. При наличии пиров выбор идёт задача → эффективный конфиг
  проекта; `auto` перебирает `auto_order`. Доступность — authenticated probe
  `ONLINE` либо свежий relay heartbeat (не старше `2 * relay_interval`).
  `here`/`auto` и ролевой выбор перед запуском сохраняются в `task.runner`
  как конкретное имя узла. Имя сопряжённого узла имеет приоритет над совпавшим
  названием роли; два laptop не получают одну реплицированную очередь.
- Удалённый launch отправляется через node-токен на
  `POST /api/v1/projects/<p>/tasks/<t>/launch`. Сначала проверяется существующий
  запуск, затем доставляются актуальные задача/тред и Git 01 snapshot
  (git remote либо LAN bundle). Store проверяется против текущего UUID
  локальной реплики: карточка пустого пира до bootstrap может содержать старый UUID.
  После authenticated probe устаревший UUID парной карточки обновляется,
  чтобы дальнейший relay использовал актуальный store. После успешного launch
  выполняется readback состояния runner; сбой readback не отменяет принятый запуск.
- Runner ставит задачу в свою локальную очередь и запускает её, когда свободны
  его slots; при выключенной очереди используется обычный start. Dispatcher
  не захватывает задачу, закреплённую за другим узлом. Сессия, проверки лимитов,
  backend/login, worktree и `$KANBAN_CMD` принадлежат runner. Машинный clone —
  общий seed: агент всегда получает отдельный worktree, даже если для обычной
  рабочей папки проекта isolation выключен.
  Импорт code refs не перемещает ветки, checkout в активных task-worktrees:
  следующий launch не блокируется первым агентом и не переписывает его ветку.
- Автоматическая очередь недоступного runner сохраняет реплицируемый
  `task.runner_request` (непрозрачный ID запроса). До записи intent snapshot
  публикуется в git remote; без remote это `SYNC_NO_REMOTE`. Только закреплённый
  runner после получения intent через обычный `kanban daemon` обновляет свой
  clone, переводит задачу в локальный `queued` и очищает request одной записью
  под board lock. На headless runner нужны `serve` для API/синка и `daemon`
  для приёма relay-intent, диспетчеризации и crash restart.
  Relay-only availability не является HTTP endpoint: intent доставляется
  обычным синком. Пока доставка не подтверждена, выключение источника не
  гарантирует приём запроса; после приёма источник не нужен.
- Stop и rerun адресуются поколению дескриптора через журнал (7.1); ответ
  реплицируется вместе с тредом и вызывает обычный resume на владельце.
  Живой `ask --wait` poller не заменяется. Таймаут или нечитаемый ответ после отправки
  launch возвращает `RUN_LAUNCH_UNCERTAIN`: mutation не повторяется, replacement
  intent не записывается. Проверять итог нужно по task/runs runner.
- Успешный launch отвечает `{session, queued}`: `session: null, queued: true`
  означает принятую очередь без локальной сессии у вызывающего узла.

### 9.3 Предложение другого runner (TASK-420)

- При `r`/`F` недоступный явный runner открывает один диалог: код, причина
  и время выключения; запуск на другом узле, ожидание выбранного узла или отмена.
  На телефоне при недоступном ноуте альтернативой является сервер.
- API `launch` принимает `runner` (`auto`/`here` тоже допустимы) и
  `on_unavailable: ask | queue | other`, по умолчанию `ask`.
  Ответ `409` содержит `error: {code, node, since, message}` и `alternatives`.
  Сам запрос `ask` не меняет размещение, фазу или сессию; диагностика может
  записать `run_failure`. Отмена не отправляет новый запрос.
- `queue` сохраняет конкретное имя runner и фазу `queued`, без локальной сессии
  и без локального runner-дескриптора. Карточка показывает ожидание узла;
  диспетчер frontend повторяет launch при возвращении выбранного runner,
  но не запускает задачу локально. Это ожидание требует живого frontend,
  в отличие от доставленного `runner_request` через relay (§9.2).
  Повторная проверка недоступности не сбрасывает очередь и не создаёт диалогов.
- `other` запускает альтернативный узел; клиент также может повторить запрос
  с `runner` из действия `run_on`. `auto`/`here` не показывают диалог.
  Без пиров существующее локальное поведение сохраняется.
- Таймаут после отправки запуска не предлагает перенос: runner мог уже принять
  запрос. `RUN_ALREADY_RUNNING` также остаётся отказом, а не предложением переноса.



## 10. Транспорт синхронизации

### 10.1 Когда синкаться

Синк полностью автоматический. На server/laptop он вызывается из `serve` и
работает без открытого TUI; на mobile — из TUI или `daemon` (2.1). Поводы:

- старт узла и выход из сна (отправляется `hello`);
- пир появился в mDNS, ответил на probe или стал достижим через tailnet;
- каждая локальная запись: push в живой поток;
- периодический pull раз в `sync.interval` (по умолчанию 30 с), страховка от
  потерянных событий.

### 10.2 Протокол обмена

1. `GET /sync/vector`: узнать вектор пира.
2. `GET /sync/ops?after=<свой вектор>`: получить недостающее страницами,
   применить (раздел 5).
3. `POST /sync/ops`: отправить то, чего нет у пира.
4. `GET /sync/stream` (SSE): пока оба онлайн, операции идут живым потоком.
   После обрыва соединения — снова шаг 1.

Сначала применяются tombstones, потом остальное. Порядок внутри
страницы — по HLC.

### 10.3 Выключение и сон

Хуки systemd (shutdown, sleep) вызывают `POST /sync/bye {reason, at}` на всех
пирах, предварительно протолкнув хвост журнала. На mobile systemd нет: `bye`
отправляет TUI/daemon при штатном выходе (`reason: exit`); у телефона нет
`NODE_POWERED_OFF` в смысле ошибки — он просто «не в сети» (2.1). Пир запоминает «ушёл в
{at}». По этой отметке `NODE_POWERED_OFF` и отличается от
`NODE_UNREACHABLE`. После старта или пробуждения узел шлёт `hello` (обычный
`/sync/vector` с отметкой), и отметка «ушёл» снимается.

### 10.4 Bootstrap новой реплики

Пустой узел после сопряжения получает полный снапшот store
(`GET /sync/snapshot`: архив store без машинно-локальных данных + `store_id` +
вектор + meta) и дальше синкается обычным образом. Номера задач выдаются
локально по разделу 6. Если оба узла непустые и `store_id` разный, это
`SYNC_STORE_MISMATCH`.

### 10.5 Реализация Sync 06 (TASK-413)

- Синкает владелец `sync/worker.lock`: serve имеет приоритет; без него воркеры
  запускаются внутри TUI или `kanban daemon` (2.1), systemd не требуется.
  Новые пиры подхватываются за `sync.interval` или сразу по hello/mDNS.
- Поводы: старт serve (hello + немедленный цикл); входящий `POST /sync/hello`
  и новое mDNS-объявление будят простаивающие workers; локальная запись любого
  процесса (TUI, CLI, колбэки агентов) видна по `sync::change_token`
  (опрос 0,5 с в serve, в событиях API и в TUI) и сразу уходит push-ем и в SSE;
  страховочный цикл раз в `sync.interval`. Вне домашней сети и при
  непогашенном `bye` пира узел к нему не обращается; записи ждут в журнале.
  Токен — смесь пути, длины и mtime активного сегмента каждого узла,
  `ahead.jsonl`, `projection.json`, `uids.json`, `conflicts.jsonl` и
  `conflicts-archive.jsonl`. Каталога `sync/` нет — токена нет.
- Цикл: `GET /sync/vector` → `{node_id, store_id, empty, vector, protocol,
  min_protocol}`; затем pull страниц
  `GET /sync/ops?after=<id:seq,…>&limit=` (по умолчанию 200, максимум 1000)
  → `{operations, next, more}`; push `POST /sync/ops {operations}` →
  `{vector}` (лимит тела 256 MiB); затем живой `GET /sync/stream?after=…`:
  SSE `event: ops`, `data:` — JSON-массив операций, keepalive раз в 15 с.
  Тишина 45 с или обрыв — новый цикл. Курсор `next` гарантирует продвижение
  даже при дырах в чужом журнале. Клиент шлёт `x-kanban-sync-protocol` (4.6).
- Страница читается из непрерывных сегментов со смещения после курсора, без
  разбора и сортировки всего журнала. `ahead` не отдаётся. Внутри страницы
  по-прежнему сначала tombstones, затем остальные по HLC; `next` — максимальный
  seq узла уже внутри обрезанной страницы. Курсор старше `compacted` —
  `409 SYNC_SNAPSHOT_REQUIRED`: нужен bootstrap (10.4), а не хвост журнала.
  Догон после разрыва идёт сегментами, пока курсор не старше прунинга; снапшот
  нужен для пустой реплики и для отставшего курсора. Дубли (push + поток)
  отбрасываются по голове сегмента.
- Ошибки `POST /sync/ops`: `409 SYNC_STORE_MISMATCH | SYNC_CLOCK_SKEW |
  SYNC_STORE_TOO_NEW | SYNC_OP_FORMAT_TOO_NEW | SYNC_PROTOCOL_MISMATCH |
  SYNC_SNAPSHOT_REQUIRED`, `400` для неверных операций. Worker пишет в лог только
  смену ошибки, чтобы выключенный пир не засорял journald.
- Mobile/outbound инициатор после push вызывает `POST /sync/ack` с
  собственными store_id и вектором: сервер не может дозвониться до него сам.
- Bootstrap: узел без проектов с чужим `store_id` берёт `GET /sync/snapshot`
  (`{node_id, store_id, vector, hlc, files}`, файлы в base64). Если пусты оба,
  снапшот берёт узел с большим `node_id`; пустой пир непустого узла просто
  ждёт. Источник сначала назначает UID ещё не тронутым доскам. В снапшот
  входят `project.yaml` (без `work_path`, `migrated_from`, `last_opened_at`),
  конфиг проекта, задачи без локальных полей, треды, `instructions/`,
  `assets/images/`, глобальный конфиг без локальных секций,
  `meta/projection.json`, `meta/uids.json`, сегменты
  `sync/journal/<node>/*.jsonl` и CAS blobs, на которые ссылаются file-операции
  и поля сущностей file. `index.json`, заглушка `state.json` и `FORMAT` не
  передаются. Приёмник пишет redo
  `sync/bootstrap.json`, ставит файлы, для формата 2 пишет `FORMAT` и заглушку
  (для формата 1 оставляет v1-файлы миграции), сохраняет свои
  секции `node/sync/serve/daemon/tui/recent_models` и последним принимает
  `store_id`; прерванная установка завершается при следующем `Journal::open`.
  Другие файлы `assets/` (CSV, JSON, каталоги артефактов агентов) и весь
  `context/` не обходятся и не передаются; приёмник также отклоняет такие пути.
  Белый список store-relative путей — `core::sync::transport::allowed_path`;
  его используют snapshot и drift reconciliation. Изображения определяются
  расположением под `assets/images/`, а не расширением файла.
  `instructions/` и `assets/images/` после bootstrap реплицируются file-операциями
  с SHA-256 ссылками на CAS (TASK-509); байтов/base64 в журнале нет.
  Снапшот пока остаётся base64 JSON в памяти: whitelist исключает артефакты,
  но не делает bootstrap потоковым.
- `kanban serve --sync` — один полный цикл со всеми пирами (для скриптов);
  `--bye` перед уведомлением проталкивает хвост журнала, недоступный пир не
  блокирует сон.

#### Сверка внешних изменений (TASK-509)

`Journal::reconcile()` вызывается при старте CLI (включая TUI/daemon/serve),
когда sync включён, перед HTTP sync cycle, выдачей vector/snapshot, приёмом
remote-операций и раундом git-relay. В serve/TUI/daemon worker сверка
повторяется с `sync.interval` только при включённом sync. Inotify не требуется.

Локальный `sync/drift.jsonl` хранит store-relative путь и `{mtime, size, hash}`
последней захваченной версии. Capture дописывает одну запись, сверка сворачивает
индекс. Она читает stat всех разрешённых файлов; содержимое хэшируется только
при изменении mtime/size. Изменение одного mtime при прежнем хэше не создаёт
операцию. Индекс не переносится между машинами: remote apply/bootstrap
записывают собственные метаданные принятых файлов.

Обход ограничен `project.yaml`, global/project config, `tasks/<status>/*.md`,
`threads/*.yaml`, `instructions/` и `assets/images/`; общие snapshot helpers
и `allowed_path` не допускают `context/` и остальные `assets/`.
Неизменившаяся доска не порождает операций. Внешние create/edit/delete
(редактор, checkout/restore, скрипт, восстановление бэкапа) проходят через
тот же capture, HLC и field-LWW, что обычная запись. Предыдущие байты
хранятся в локальном CAS, чтобы удаление YAML-поля стало delta `null`, а
удаление файла — tombstone. Перенос task между статусами сохраняет UID;
thread lifecycle отдельно передаёт удаление/создание даже пустого треда.

Сканирования нет в горячем пути task write. Сверка берёт блокировки в порядке
store → boards → sync; она не вызывается из write-lock задачи. Внешний capture
не переписывает наблюдаемый файл, в том числе при redo после падения:
последующая правка редактора остаётся для следующей сверки. Обычный capture
и remote apply обновляют индекс вместе со своими redo-транзакциями.
Разорванный последний append индекса отбрасывается при восстановлении.
При первом запуске без индекса существующие файлы захватываются как baseline.
Повреждённый YAML останавливает сверку с ошибкой, не объявляется удалением.
Как у stat-first индекса, изменение байтов с принудительно сохранёнными
**одновременно** mtime и размером не обнаруживается.

Для инструкций и картинок `entity=file`, `id` — board-relative путь,
`set.blob` — SHA-256; `set.path` фиксирует тот же путь при создании.
CAS находится в `sync/blobs/<sha256>`; имя и содержимое проверяются.
HTTP передаёт бинарные bytes через аутентифицированные
`GET/PUT /sync/blobs/{hash}` (PUT ≤256 MiB), до отправки/применения операций.
Pull и SSE сначала получают недостающие blobs; push сначала загружает их.
Отсутствующий или повреждённый blob не подтверждается как применённая операция.
Git-relay кладёт blobs отдельными Git objects рядом с batch; при
`relay_encrypt=true` и batch, и blobs шифруются age. Хэши остаются ссылками,
в journal/batch нет base64. Неиспользуемый blob старше часа удаляет прунинг
(4.5); моложе часа и любая живая ссылка (drift, поле file, удерживаемая
операция, `remote-pending.json`) сохраняются.

Приёмка: `cargo test --locked --test sync_drift_test`; HTTP/blob и encrypted
relay покрыты существующими sync/relay integration suites. Бенчмарк:
`cargo test --release --locked --test sync_drift_test benchmark_reconcile_2000_files -- --ignored --nocapture`.


### 10.6 Абстракция транспорта и git-relay (TASK-440)

Протокол обмена (10.2) не зависит от того, как доставляются операции.
Транспорт — один из двух видов:

| Транспорт | Пути | Что умеет |
|---|---|---|
| direct http | LAN; tailnet (system — напрямую по tailnet-IP, managed — через SOCKS5 `127.0.0.1:<socks_port>`) | всё из 10.5: vector/ops/stream, snapshot, `/git`, launch/stop, live-лог |
| git-relay | `sync.relay_remote` или origin проектов | журнал операций (включая stop/rerun/answer), heartbeat и bounded log tail; без snapshot/direct launch/live-follow |

HTTP использует LAN → tailnet. Relay-воркер независимо публикует резервный
журнал и heartbeat, поэтому работает без домашней сети и без Tailscale,
в том числе на outbound-only mobile. Direct остаётся live-путём.

git-relay:

- Каждый узел пишет только свой ref `refs/kanban/sync/<node_id>`:
  append-only цепочка коммитов, в каждом — пачка операций своего журнала
  (JSONL). Force-push не используется; чужие refs только читаются.
- `fetch` всех `refs/kanban/sync/*` раз в `sync.relay_interval` (по умолчанию
  60 с) и после каждой своей пачки push. Полученные операции идут через
  `apply_remote` как обычно; дедупликация по `op_id` (5.6).
- Опция `sync.relay_encrypt` (age; получатели — ключи сопряжённых узлов из
  `peers.yaml`) шифрует содержимое пачек. Без неё relay доступен всем, у кого
  есть доступ к remote.
- В relay никогда не попадают токены, `peers.yaml`, `node.yaml`, состояние
  Tailscale и прочие машинно-локальные данные (раздел 3): туда пишутся только
  реплицируемые операции.
- Цепочка сохраняется целиком: автоматического удаления/пересборки relay refs
  нет. Если у ref уже есть коммит, а локальный прунинг ушёл дальше
  опубликованного seq, цикл отказывается с `SYNC_RELAY_GAP` и не дырявит
  цепочку. Первый коммит родителя не имеет: префикс, который HTTP-пиры уже
  подтвердили и журнал упростил, в relay не повторяется; пир без этого
  префикса получает `SYNC_RELAY_GAP` при чтении, а не тихое применение дыры.
- Relay используется, когда direct недоступен, например tailscale.com
  заблокирован, а хостинг remote доступен.

Реализация TASK-440:

- Локальный bare-кэш: `<store>/sync/relay/<sha256(remote)>/git`; рабочий
  checkout, index и refs кода проекта не меняются. После сбоя push повторяется
  с сохранённого локального tip; при потере кэша цепочка продолжается от remote.
  Форк собственного ref и откат чужого ref отвергаются. Чужие refs принимаются
  только для сопряжённых node_id того же store; автор каждой операции должен
  совпадать с владельцем ref. Remote — доверенный транспорт: age обеспечивает
  конфиденциальность, но не подпись автора.
- Один commit содержит только `batch.jsonl` либо `batch.age`. Первая строка
  расшифрованного JSONL — `{node_id, store_id, at_ms, vector}`, остальные —
  операции автора. Векторы/heartbeat шифруются вместе с операциями. Применение
  идёт через обычный redo/LWW/HLC путь; повтор HTTP + relay безопасен.
- `sync.relay_remote` — локальный URL/путь отдельного store-репозитория.
  Без него используются уникальные origin зарегистрированных проектов.
  Нужны уже сопряжённые пиры; без пиров ничего не публикуется. **Каждый remote
  получает журнал всего store**, поэтому используйте отдельный приватный
  remote или age, если проекты имеют разные права доступа.
- `sync.relay_interval` — положительное число секунд, default 60; heartbeat
  публикуется даже без новых операций. Локальная запись вызывает ранний push
  и fetch. `serve --sync` принудительно выполняет цикл и печатает
  `synced with git-relay` при доставке в remote (это не подтверждение live-пира).
  Те же воркеры запускаются из serve/TUI/daemon.
- `serve --probe` и `/nodes` возвращают `ONLINE`, `path: relay`, если direct
  недоступен, а heartbeat сопряжённого узла не старше `2*relay_interval`.
  Время из будущего не считается свежим. `core::sync::relay::available`
  предоставляет тот же критерий доступности для выбора runner `auto`;
  relay не превращает heartbeat в HTTP endpoint для запуска.
- Для `sync.relay_encrypt: true` установите `age` и `age-keygen` на всех узлах
  **до повторного сопряжения**. Pairing создаёт локальный
  `sync/relay-age.key` (0600), обменивается публичными получателями и хранит их
  в `sync/peers.yaml` как `relay_recipient`. В пачку включены собственный ключ
  и ключи всех пиров. Если ключ пира отсутствует, push отказывает с
  `SYNC_RELAY_KEY_MISSING`; plaintext fallback отсутствует. Старые открытые
  коммиты после включения age остаются открытыми; используйте новый приватный
  remote, если прежняя история должна быть недоступна.
  Новый пир сначала получает HTTP bootstrap: его вектор позволяет пропустить
  старые зашифрованные пачки, где ещё не было его получателя. Relay читает
  историю от tip назад только до покрытия недостающего непрерывного префикса.
- `relay_encrypt` реплицируется; remote, interval, age identity, recipients,
  presence, git-кэш и весь `net` остаются машинно-локальными. Git/age subprocess
  ограничен 120 с (`SYNC_RELAY_TIMEOUT`); диагностические stderr с возможными
  credentials в URL не выводятся.


## 11. Протокол `serve`

`kanban4ai serve` — подкоманда того же бинаря, отдельного Cargo target нет.
Устанавливается как systemd user-unit (пакеты AUR, `install.sh`).

### 11.1 Сеть и версия

- HTTP/1.1. Bind только на адреса из LAN-подсетей `sync.home_networks` (CIDR).
  Без них bind — на адреса приватных диапазонов. На loopback serve отвечает
  всегда. Порт `serve.port`, по умолчанию `7420`. При `net.tailscale.mode:
  system` serve дополнительно слушает tailnet-IP узла, а `100.64.0.0/10`
  входит в `home_networks` (11.5). На mobile serve слушает только loopback.
- mDNS: сервис `_kanban4ai._tcp`, TXT `node_id`, `name`, `role`, `proto`.
  Статические адреса пиров в `peers.yaml` — запасной вариант.
- Версия протокола — целое число `proto` (сейчас `1`). Узел объявляет
  `proto` и `min_proto`. Пиры совместимы, если версии каждого попадают в
  диапазон другого, иначе `NODE_VERSION_MISMATCH`.
- Клиентский API — `/api/v1/…`. В `v1` разрешены только добавления
  (новые эндпоинты и поля, неизвестные поля клиент игнорирует). Ломающее
  изменение — только `/api/v2` с сохранением `v1` на переходный период.

#### Реализация Serve 01 (TASK-410)

`kanban4ai serve [--port PORT]` работает в foreground со всем store; разрешение
проекта не требуется. Явный запуск команды не зависит от `serve.enabled`
(этот флаг предназначен для управления из Settings). CIDR и порт читаются из
`<store>/config.yaml`; `--port` переопределяет порт. Ошибочный CIDR, порт 0
или занятый выбранный адрес останавливают запуск целиком.

```yaml
serve:
  port: 7420
  shutdown_timeout: 10       # секунды graceful drain после SIGINT/SIGTERM
sync:
  home_networks: [192.168.0.0/24, fd00::/8]
```

При пустом `home_networks` используются RFC1918 IPv4 и IPv6 ULA (`fc00::/7`).
Loopback включается независимо от CIDR. Wildcard bind (`0.0.0.0`, `::`) не
используется: сервер слушает отдельные адреса активных интерфейсов, выбранные
при запуске. После смены адреса интерфейса сервис нужно перезапустить.
После сигнала listeners закрываются, текущие соединения получают период
`shutdown_timeout` (по умолчанию 10 с), затем оставшиеся закрываются.

Установка: AUR кладёт `kanban4ai-serve.service` в `/usr/lib/systemd/user/`;
`sh scripts/install.sh --with-serve` — в пользовательский каталог systemd с
учётом `PREFIX` и `DESTDIR`. Автоматического включения нет:
`systemctl --user enable --now kanban4ai-serve.service`.
Логи: `journalctl --user -u kanban4ai-serve.service`.

Публичные probes реализованы в этой задаче; сопряжение — в TASK-411,
обнаружение/mDNS и статусы — в TASK-412; sync/git и клиентский API —
в TASK-413…TASK-414 и TASK-418.
Неизвестный защищённый путь без токена возвращает 401, с разрешённым токеном —
404; это не реализация будущего endpoint.


### 11.2 Аутентификация

- `Authorization: Bearer <token>`. Токен — 256 бит случайных данных. Для входящих
  токенов узел хранит только хеш (`tokens.yaml`, 0600).
- Единственный вид токенов — **node** (пир: синк, git, API).
  Client-роль и выпуск client-токенов удалены; телефон сопрягается как node.
  При запуске serve-команд старые client-записи удаляются из tokens.yaml;
  хеши сопряжённых node-токенов сохраняются.
- Сопряжение (TASK-411):
  - ноут ↔ сервер: одноразовый 6-значный код, живёт 5 мин, не больше 5
    попыток. `POST /pair {code, node_card}` возвращает node-токены в обе
    стороны;
  - телефон (узел роли `mobile`, TASK-432): узел показывает QR с
    `{address, port, node_id, code}`, где `address` — LAN-IP или MagicDNS-имя
    tailnet. Телефон сканирует его и выполняет тот же `POST /pair` со своей
    карточкой (`role: mobile`, `dial: outbound`; `address` можно опустить —
    входящих соединений нет).
- Отзыв токена делается в UI вкладки Sync. Отозванный токен получает
  `401 NODE_AUTH_FAILED`.
- TLS нет. В LAN это осознанный риск: токен виден в сети, к которой есть
  доступ только у владельца. В tailnet трафик шифрует WireGuard; в relay
  токены не попадают (10.6).

Для скриптов `kanban4ai serve --issue-token node` создаёт секрет из
32 случайных байт, печатает его один раз как 64 hex-символа и завершает работу.
Записи атомарно сохраняются под sync lock в `<store>/sync/tokens.yaml`, 0600:

```yaml
tokens:
  - kind: node
    sha256: "<64 lowercase hex символа SHA-256 от ASCII bearer-токена>"
```

Файл машинно-локален. Сервер перечитывает его на каждом защищённом запросе:
удаление записи отзывает токен без рестарта. Отсутствующий файл означает,
что разрешённых токенов нет; повреждённый файл закрывает доступ с 500
`INTERNAL_ERROR`, не отключает проверку. `/health` и `/version` остаются публичными.

#### Реализация Serve 02 (TASK-411)

CLI работает на глобальном store (`KANBAN_HOME`), без выбранного проекта:

```sh
# На сервере (serve уже запущен либо будет запущен отдельно):
kanban4ai serve --pair-code
# На ноуте: код с сервера и адрес самого ноута, доступный серверу:
kanban4ai serve --pair 192.168.1.2:7420 --code 123456 --address 192.168.1.3:7420
# На сервере: JSON и терминальный QR с одноразовым кодом для mobile:
kanban4ai serve --phone-qr 192.168.1.2:7420
# На телефоне (node.role: mobile): адрес самого телефона не нужен:
kanban4ai serve --pair 192.168.1.2:7420 --code 123456
# Отзыв по sha256 из sync/tokens.yaml; действует без рестарта serve:
kanban4ai serve --revoke-token <sha256>
```

`node.name` и `node.role` задаются в глобальном конфиге до сопряжения.
Идентичности и имена должны различаться; уникальна только роль server.
`--pair` принимает LAN IP:port (IPv6 — `[addr]:port`), не hostname;
использует `curl`, без proxy и перенаправлений, с ограниченным временем запроса.
`--address` — доступный пиру адрес локального inbound-узла; для mobile необязателен.
Адрес сервера у инициатора сохраняется из `--pair`, а не из автоматически выбранного интерфейса сервера.

`POST /pair` принимает `{code, node_card}`. `node_card` содержит
`node_id`, `name`, `role`, `dial`, `store_id`, `address` (IP:port), `empty`, `proto`,
`min_proto`. `empty` означает отсутствие зарегистрированных проектов.
Ответ: `{node_card, token, reverse_token}`: `token` принимается сервером,
`reverse_token` — инициатором. Это два независимых случайных 256-битных секрета.
При разных store_id двух непустых узлов ответ — `SYNC_STORE_MISMATCH`;
несовместимый протокол — `NODE_VERSION_MISMATCH`. Для пустого узла смена
store_id и получение данных выполняются последующим bootstrap, не `/pair`.

`sync.peers` в глобальном `config.yaml` содержит карточки пиров без токенов.
`sync/peers.yaml` — список `{node_id, token, inbound_sha256, address, addresses}`:
исходящий bearer-секрет, fingerprint входящего токена, основной статический
`IP:port` и необязательный список запасных адресов. Старые записи без адресов
используют `sync.peers[].address`. В `sync/tokens.yaml` остаются только хеши
входящих токенов; сырой исходящий секрет необходим HTTP-клиенту.
Повторное сопряжение того же node_id заменяет исходящий секрет и отзывает
предыдущий входящий токен. Все записи атомарны; изменения списка держат
store lock, затем sync lock. Секретные файлы имеют права 0600 и не реплицируются.

Новый `--pair-code` заменяет предыдущий код. `sync/pair-code.yaml` хранит
только хеш, срок действия и счётчик попыток, права 0600. Попытки считаются
под sync lock, в том числе неверные коды; пятая неудачная попытка блокирует
правильный код. Успешный код потребляется до выпуска токенов.
Параметры `sync.pairing.code_ttl_seconds` (1…300, по умолчанию 300) и
`sync.pairing.code_max_attempts` (1…5, по умолчанию 5) позволяют ужесточить
ограничения. Создание кода и отзыв не требуют перезапуска HTTP-сервиса.
`--phone-qr [HOST:PORT]` печатает строку payload `{address, port, node_id,
code, role: "mobile", dial: "outbound"}`, затем команду для телефона
`kanban4ai join CODE@HOST:PORT` и QR этой команды (TASK-499). `address` —
LAN-IP или MagicDNS-имя (без аргумента: LAN IPv4 интерфейса с маршрутом по
умолчанию, затем других поднятых интерфейсов, иначе MagicDNS),
`code` — тот же одноразовый 6-значный код; приглашение не шифруется. QR и
приглашение передавайте только владельцу телефона. kanban4ai камеру не
сканирует: текст из QR копируется сканером телефона и вставляется в терминал
или в TUI Sync → Pair with a node (поле адреса, код пустой). `join` делает
узел `mobile`/outbound (имя `phone`, если не задано `--name` и узел ещё не
mobile; на server отказ), для tailnet-адреса переводит `net.tailscale.mode`
из off в managed и выполняет `net up` (при отсутствии бинарей — `net
install`), затем `serve --pair` и один цикл sync.

#### Реализация Serve 03 (TASK-412)

- `serve` анонсирует `_kanban4ai._tcp.local.` с TXT `node_id`, `name`, `role`,
  `proto` и слушает объявления других узлов. mDNS работает только на разрешённых
  LAN-интерфейсах, без loopback; ошибка mDNS не отключает статические адреса.
  Объявление не сопрягает узлы: идентичность подтверждается парным bearer-токеном
  и `node_id` из защищённого `/node`. Новое объявление запускает проверку даже
  при сохранённом bye: пропущенный hello не оставляет узел навечно «выключенным»;
  сама запись mDNS не снимает bye без подтверждённого контакта.
- `kanban serve --discover` собирает объявления в течение `sync.probe_timeout`
  и выдаёт JSON с адресами, без собственного узла. `kanban serve --probe` и
  защищённый `GET /nodes` возвращают `{node, status, code, message, since,
  last_seen}` для всех сопряжённых пиров. Фоновые probes выполняются каждые
  `sync.interval` секунд. `node` — UUID; тексты используют роль «Сервер»/«Ноут».
- Настройки `sync.home_networks`, `probe_timeout` (секунды, по умолчанию 3),
  `interval` (секунды, 30), `max_skew` (секунды, 300) машинно-локальны.
  Нулевые timeout/interval запрещены. Вне домашней сети probes не обращаются к
  пирам. Без `home_networks` домашней считается активная private IPv4 / ULA IPv6
  сеть; один loopback не считается присутствием в LAN.
- Адреса из mDNS проверяются первыми, затем основной/запасные статические адреса
  из `peers.yaml`, затем карточка в конфиге. Ошибки одного адреса не мешают
  проверить остальные; HTTP redirects и proxy из окружения отключены.
- `sync/presence.yaml` — атомарная машинно-локальная запись под sync lock:
  последний подтверждённый контакт, `{reason, at}` ухода и обнаруженные адреса.
  Отметка `bye` переживает перезапуск. Поздний `bye`, старше последнего контакта,
  не отменяет новое состояние. Обычный отказ соединения без `bye` —
  `NODE_SERVICE_DOWN`, таймаут — `NODE_UNREACHABLE`; случайное завершение serve
  не выдаётся за выключение хоста.
- `kanban serve --bye shutdown|sleep` отправляет `POST /sync/bye {reason, at}`
  всем пирам; `--hello` отправляет `POST /sync/hello`. `serve` также шлёт hello
  при старте. Эти методы принимают только токены сопряжённых узлов; отправитель
  определяется по fingerprint, а не по переданному UUID. Hello и свежий
  защищённый контакт и подтверждённый ответ на исходящий hello снимают отметку
  ухода. `/sync/vector` тоже считается контактом, а `--bye` сначала
  проталкивает хвост журнала (10.5).

Systemd-хуки — **system**, не user units: пользовательский manager не получает
`sleep.target`. AUR устанавливает `kanban4ai-sleep@.service` и
`kanban4ai-shutdown@.service` в `/usr/lib/systemd/system`, не включает их.
`scripts/install.sh --with-serve` кладёт их в
`$PREFIX/share/kanban4ai/systemd`; администратор копирует их в
`/etc/systemd/system` и выполняет `sudo systemctl daemon-reload`.
Включение для пользователя `USERNAME`:

```sh
sudo systemctl enable kanban4ai-sleep@USERNAME.service
sudo systemctl enable --now kanban4ai-shutdown@USERNAME.service
```

Sleep hook шлёт bye перед `sleep.target`, hello — при его остановке после
пробуждения. Shutdown hook остаётся активным до выключения и шлёт bye до
остановки сети. Используется store пользователя; для нестандартного store
нужен drop-in с `Environment=KANBAN_HOME=/absolute/store`.
Таймауты hooks — 20 с, допускают systemd override; недоступный пир не блокирует
сон/выключение. Отключение/ручная остановка shutdown hook также отправляет bye.

#### Реализация API operations (TASK-414)

- `/api/v1/projects` возвращает `{projects: [{id, name}]}`; `…/board` —
  `{columns, tasks}`; `GET …/tasks/<t>` — `{task, runs, conflicts}`.
  `runs` — карта дескрипторов по UUID узла. `…/thread` возвращает тред.
  JSON задачи включает Markdown `description`, но не локальные поля сессии,
  worktree, integration и пути контекста.
- `POST …/tasks` принимает `title` и поля настройки задачи; `PATCH …/<t>`
  принимает частичную правку тех же полей. Nullable-поля можно очистить через
  `null`; неизвестные и локальные поля отвергаются. Смена колонки — только
  `POST …/move {status}`, не PATCH: она вызывает `Operations::move_task`.
- В дополнение к таблице доступен `POST …/ask {text, variants?}`; ответ —
  `POST …/answer {message: "MSG-NNN", text}`. Ответ содержит
  `{task, remaining, resumed_session, queued}`. Побочные эффекты вопросов,
  ответов и переходов выполняются обычными operations.
- API-записи по умолчанию `human`, независимо от окружения процесса serve.
  Node-токен допускает `agent: true` для `move`/`ask`.
  Правила ролей и колонок проверяет operations.
- `POST …/launch {runner?}` отправляется сопряжённому runner через node-токен.
  До отправки проверяются LAN/tailnet, bye, идентичность, текущий store и
  совместимость протокола. После таймаута mutation не повторяется:
  запуск мог уже состояться. Явный launch-runner меняет размещение задачи (9.2).
- `POST …/stop {}` и `POST …/rerun {}` выполняются локально либо сохраняют
  адресованный последнему runner journal intent (7.1). Ответ сообщает принятие
  запроса, не подтверждает остановку/новый запуск. Реплицированный ответ на
  вопрос сам запускает runner-local wake; HTTP resume для доставки не нужен.
- `/events?project=<id>` — авторизованный SSE: `ready` при подключении,
  `board` с `{refresh: true}` при изменении задач, тредов, сессий, sync или
  presence. Клиент перечитывает нужный API; подключение не является журналом
  с replay. Опрос файлов раз в 0,5 с замечает записи CLI/TUI и других процессов;
  комментарий keepalive отправляется раз в 15 с.


### 11.4 Формат ошибок

Любая ошибка возвращается так:
`{"error": {"code", "message", "node"?, "since"?, "last_seen"?, "details"?}}`.
`message` — готовый текст для UI из раздела 13 с подставленными значениями.
Клиент показывает `message`, а логику строит по `code`.

| HTTP | Когда |
|---|---|
| 400 | неверный запрос |
| 401 | `NODE_AUTH_FAILED` |
| 403 | правило колонок/ролей (текст ошибки operations как есть) |
| 404 | нет проекта/задачи |
| 409 | `RUN_ALREADY_RUNNING`, runner недоступен (`NODE_*`), `SYNC_STORE_MISMATCH` |
| 426 | `NODE_VERSION_MISMATCH` |
| 502/504 | проксирование на пир не удалось (`NODE_*` пира) |

### 11.5 Сеть / Tailscale (TASK-431, TASK-433…TASK-435)

Мобильный клиент (PWA, TASK-425/426) отменён: телефон — узел `mobile` (2.1).
Вне дома узлы находят друг друга через tailnet.

**Почему userspace-sidecar.** На Android одновременно работает только один
VpnService, а он занят вендорским VPN без возможности настройки. Поэтому на
телефоне Tailscale не ставится как VPN: kanban4ai запускает `tailscaled` в
userspace-режиме как обычный процесс внутри proot. Для Android это просто
трафик приложения, и он идёт через вендорский VPN, как любой другой. Наружу
sidecar отдаёт SOCKS5 на loopback, и kanban4ai ходит к пирам через него.
Нативной Rust-библиотеки Tailscale нет, поэтому это отдельный процесс.

Режим `net.tailscale.mode`:

| Режим | Где | Что делает kanban4ai |
|---|---|---|
| `off` | по умолчанию | tailnet не используется |
| `system` | server, laptop | обычный `tailscaled` от systemd с ядерным tun; kanban4ai им не управляет, только читает статус. serve слушает tailnet-IP, `100.64.0.0/10` входит в `home_networks` (11.1) |
| `managed` | mobile | sidecar `tailscaled --tun=userspace-networking --socks5-server=127.0.0.1:<socks_port> --statedir=<store>/net/tailscale`; запуск, наблюдение, перезапуск |

Ключи в локальном `<store>/config.yaml` (секция `net`, не реплицируется):

```yaml
net:
  tailscale:
    mode: managed            # off | system | managed
    hostname: kanban-mobile  # по умолчанию kanban-<role>
    socks_port: 1055
    auth_key_file: null      # необязательно: одноразовый auth key, удаляется после входа
```

- `<store>/net/tailscale/` — state dir sidecar (ключи машины): каталоги 0700
  (0600 не позволяет входить в каталог), файлы 0600; приватный socket 0600
  лежит рядом, в `<store>/net/tailscale.sock`. Всё машинно-локально, не
  реплицируется и не попадает в bootstrap и relay.
- Бинарь: PATH (`pacman -S tailscale` в Arch внутри proot), затем
  `<store>/net/bin/{tailscale,tailscaled}`. `kanban4ai net install` получает
  stable static tarball amd64/arm64 с pkgs.tailscale.com, проверяет SHA-256
  и извлекает только два точных regular-file члена архива. Ссылки, дубликаты
  и неполная пара отвергаются до установки.
- Жизненный цикл managed: sidecar стартует вместе с TUI/daemon/serve и
  останавливается при выходе; один владелец под store-local lock, остальные
  процессы наблюдают его. На Linux parent-death signal убирает sidecar также
  при аварийном завершении владельца. Если Android его убил, следующий тик
  запускает новый. Падение без восстановления — `NET_TAILSCALE_SIDECAR_DOWN`.
  Отдельный `net up` оставляет daemon до `net down`; следующий TUI/daemon/serve
  забирает его под свой жизненный цикл. `net down` запрещает автоматический
  рестарт до следующего `net up`.
- Вход: кнопка `[Подключить]` показывает URL и QR входа Tailscale; либо auth
  key из `auth_key_file`. Состояние сохраняется, повторный вход не нужен (на
  узлах стоит отключить key expiry в админке Tailscale).
- Адреса пиров: `sync.peers[].tailscale_address` в store config и необязательное
  `tailscale_address` в `sync/peers.yaml` задают `host:port` запасного tailnet-адреса:
  `kanban-server.<tailnet>.ts.net:7420`, CGNAT IP или Tailscale IPv6.
  Существующий `address: IP:port` сохраняется. Сначала пробуются LAN-адреса,
  затем tailnet; в `off` tailnet исключён. В managed HTTP и SSE используют
  внутренний SOCKS5h proxy на loopback: MagicDNS разрешается sidecar, а не
  локальным DNS. LAN остаётся прямым; system использует системный tun напрямую.
  При сопряжении каждый включённый узел объявляет `Self.DNSName` из
  `tailscale status --json` (без завершающей точки) с портом serve; адрес
  сохраняется в обеих карточках `sync.peers` и `sync/peers.yaml`.
  `serve --pair HOST:PORT` и `serve --phone-qr HOST:PORT` принимают MagicDNS
  либо tailnet-IP при включённом tailnet. QR сохраняет имя хоста и порт;
  токены и проверка одноразового кода не меняются.
  В system serve добавляет CGNAT и Tailscale IPv6 к разрешённым адресам
  слушателей даже при явно заданных `home_networks`; при пустом списке
  сохраняются стандартные частные LAN-диапазоны. mDNS остаётся LAN-discovery.
  Если оба direct-пути недоступны, операции доставляются через git-relay (10.6).
- CLI: сначала задать `net.tailscale.mode` в машинно-локальном store config;
  `net up [--auth-key-file PATH]` относится к managed и не включает его неявно. При необходимости
  входа печатаются URL и терминальный QR, команда возвращает
  `NET_TAILSCALE_LOGIN_REQUIRED`; после входа повторить `net up` или проверить
  `net status`. Ключ передаётся Tailscale по имени файла, не в argv как секрет;
  файл удаляется только после подтверждённого успешного входа.
  В managed `net down` отключает, `net logout` удаляет вход. В system обе
  команды и `net up` отказываются менять установленный daemon: вход и
  systemd-сервис настраивает администратор через системный `tailscale`.
  `net status` в обоих режимах печатает JSON
  Tailscale (`CurrentTailnet`, `User`, `Self.TailscaleIPs`, `Peer[].CurAddr/Relay`)
  и локальный mode. Пустой `CurAddr` при `Relay` означает DERP.
- Человек работает
  через Settings → Sync → блок «Сеть» (TASK-434): статус (аккаунт, tailnet-IP,
  пиры онлайн, путь direct/DERP), кнопки `[Подключить]`, `[Отключить]`,
  `[Выйти из аккаунта]`. Переключение режима применяется сразу, System —
  только чтение; управлять системным daemon надо через системный Tailscale.
  Поле `Auth key` маскируется, принимает paste и не сохраняется в конфиге:
  приватный временный файл удаляется после успешного или неудачного входа.
  Статус обновляется с настроенным TUI-интервалом; экран входа закрывается
  после `Running`. На ширине 40–60 колонок Sync занимает доступную область,
  детали переносятся, при нехватке места для QR остаётся полная ссылка.
- Нужен доступ к `controlplane.tailscale.com`, `login.tailscale.com`,
  `derp*.tailscale.com:443`, желательно UDP 41641; без UDP Tailscale работает
  через DERP поверх HTTPS. Если tailscale.com недоступен — git-relay (10.6).
  Работоспособность в proot при вендорском VPN проверяет спайк TASK-431.

Спайк TASK-431: [инструкция и матрица проверок на телефоне](android-spike.md),
скрипт `docs/android-spike.sh`. Открытие login.tailscale.com уже подтверждено
человеком; вход daemon, SOCKS health, фоновые ограничения Android и смена сети
требуют отдельного прогона на телефоне. До него managed-путь — непроверенное
допущение; при неудаче используется только git-relay (TASK-440 / Sync 08).

## 12. Статус узла

### 12.1 Probe

Probe выбирает **путь** до пира, затем по нему — статус. Пути по приоритету:

| Путь | Когда | Текст |
|---|---|---|
| `lan` | этот узел в `sync.home_networks` и пир ответил по LAN-адресу (mDNS/статический) | «LAN» |
| `tailnet_direct` | ответ по tailnet-адресу, Tailscale сообщает прямое соединение | «tailnet, напрямую» |
| `tailnet_derp` | ответ по tailnet-адресу через DERP-ретранслятор | «tailnet через DERP» |
| `relay` | прямого канала нет, есть свежие (за `3 × sync.relay_interval`) данные пира в git-relay | «через git ({ago})» |
| `none` | ничего из перечисленного | «нет связи» |

Вне домашней сети LAN-путь пропускается (`NODE_OUT_OF_LAN` — это не ошибка, а
отсутствие LAN-пути; если найден другой путь, показывается он). Статус на
выбранном пути, первый сработавший шаг даёт код:

1. Ни одного пути (`none`) и этот узел вне LAN → `NODE_OUT_OF_LAN` как
   статус пути; при `none` в LAN — шаги 2–3 по LAN-адресам.
2. Есть отметка `bye` и с тех пор контакта не было → `NODE_POWERED_OFF`.
3. TCP connect: отказ (RST) → `NODE_SERVICE_DOWN`. Таймаут
   (`sync.probe_timeout`, 3 с) → `NODE_UNREACHABLE`.
4. `/version` несовместим → `NODE_VERSION_MISMATCH`.
5. `/node` возвращает 401 → `NODE_AUTH_FAILED`.
6. `store_id` другой → `SYNC_STORE_MISMATCH`.
7. Часы расходятся больше `max_skew` → `SYNC_CLOCK_SKEW`.
8. Иначе `ONLINE` (с путём). На пути `relay` шаги 3–5 не выполняются:
   статус — `ONLINE` через relay; journal stop/rerun/answer доступны,
   прямой launch/live-лог недоступен (показывается cached tail).

Для пира роли `mobile` любой не-`ONLINE` результат показывается нейтрально
(«Телефон: был в сети {ago}»), без кода (2.1).

### 12.2 Карточка узла

Это `GET /node`, пир кэширует её в `peers.yaml`. Поле `wol` есть только у узла
с ролью `server`:

```yaml
wol:
  mac: "a8:a1:59:xx:xx:xx"      # MAC LAN-интерфейса хоста, который будится
  broadcast: "192.168.0.255"    # куда слать magic packet
  port: 9                       # необязательно, по умолчанию 9
```

Пир хранит последнюю карточку, поэтому разбудить узел можно, когда тот уже
выключен.

### 12.3 Wake-on-LAN (TASK-427)

- Кнопка `[Разбудить сервер]` появляется при статусе `NODE_POWERED_OFF` или
  `NODE_UNREACHABLE` у узла с `wol`: во вкладке Sync и в диалоге раздела 9.
  У ноута такой кнопки нет.
- `POST /nodes/<id>/wake` → узел, принявший запрос, шлёт magic packet в
  свою LAN и отвечает `202`. Статус узла становится «Будим сервер…» до
  появления узла или до таймаута `sync.wake_timeout` (180 с). По таймауту —
  `NODE_WAKE_FAILED`.
- Если узел, принявший запрос, сам вне LAN, ответ — `409 NODE_OUT_OF_LAN`.
  Телефон вне дома может попросить разбудить сервер узел в LAN (ноут),
  достижимый через tailnet.
- Опция `sync.auto_wake` (по умолчанию выкл): будить автоматически, если
  задача стоит в очереди «ждать сервер».

## 13. Коды ошибок и тексты для UI

`{node}` — человеческое имя узла в именительном падеже с заглавной буквы
(«Сервер», «Ноут»; берётся из роли, иначе `name`). Время — локальное, `HH:MM`;
если не сегодня, то `DD.MM HH:MM`. `{ago}` — «3 мин назад». Эти тексты
используют TUI и API (`message`). Для `mobile` — «Телефон».

### 13.1 Узлы и синхронизация

| Код | Когда | Текст для UI | Что предлагает UI |
|---|---|---|---|
| `NODE_POWERED_OFF` | узел объявил выключение или сон (`bye`) | «{node} выключен с {since}» (для сна: «{node} спит с {since}») | разбудить (если есть `wol`), запустить на другом узле, ждать |

### 13.2 Запуски

Код хранится в задаче (`run_failure`) и треде от `kanban`; локальный failed
descriptor также получает код отказа backend/repository. `RUN_NODE_*` наблюдает
пир и **не** записывает в чужой runner-owned descriptor (раздел 7.2).

| Код | Когда | Текст для UI | Дальше |
|---|---|---|---|
| `RUN_NODE_POWERED_OFF` | runner объявил выключение или сон посреди запуска | «Прервано: {node} выключился в {at}» | при возвращении узла — crash-restart по существующим правилам; иначе `[Перезапустить на {other}]` |
| `RUN_NODE_UNREACHABLE` | heartbeat дескриптора пропал без `bye` дольше порога crash-detect | «Нет связи с {node} с {last_seen}: запуск мог прерваться» | то же; если узел вернулся и сессия жива, код снимается |
| `RUNNER_BACKEND_MISSING` | на runner нет бэкенда или он не залогинен | «На {node} нет {backend} или он не залогинен» | `[Запустить на {other}]` |
| `RUNNER_REPO_MISSING` | на runner нет клона проекта или снапшота | «На {node} нет копии проекта {project}» (снапшот: «…не получен снимок рабочей папки») | повторить после синка git, `[Запустить на {other}]` |
| `RUN_ALREADY_RUNNING` | попытка второго запуска, пока активен запуск на другом узле онлайн | «Задача уже выполняется на {node} с {since}» | `[Открыть]` `[Остановить там]` |
| `RUN_DUPLICATE` | после слияния найден двойной запуск, сделанный во время разрыва | «Задачу запускали и на {node_a}, и на {node_b}, пока узлы не видели друг друга. Сохранены обе ветки — выберите в Review» | выбор ветки в Review |

Если runner недоступен **в момент запуска**, это не код запуска: диалог
раздела 9 показывает соответствующий `NODE_*`.

## 14. Сценарии

### 14.1 Ночь на сервере → утро на ноуте

1. Вечером на ноуте задачи ставятся с runner = server (или `auto`). Запуск
   уходит на сервер. Ноут засыпает и шлёт `bye`.
2. Ночью сервер работает: колбэки агентов пишут в его реплику, журнал сервера
   растёт. Ноут на вкладке Sync сервера показывает «Ноут спит с 23:40».
3. Утром ноут просыпается и шлёт `hello`. По `/sync/ops?after=…` он получает
   ночные операции, затем `kanban/TASK-N` через `/git/…/bundle`; landing
   выполняется в рабочую папку ноута. Шапка: «Синхронизировано с Сервер 2 с
   назад». Нажимать ничего не нужно.
4. Если человек начал править раньше, чем закончился догон, ничего не
   блокируется: правки разных полей сливаются, конфликт возможен только по
   одному и тому же полю.

### 14.2 Поездка офлайн

1. Ноут вне дома. Если tailnet работает, синк с сервером продолжается по
   tailnet, и поездка ничем не отличается от дома. Дальше — случай без
   tailnet и relay: путь `none`, `NODE_OUT_OF_LAN`. Шапка: «Офлайн с 18:02,
   14 операций ждут отправки».
2. Новые задачи получают локальные номера `max + 1` (раздел 6). Ответы,
   правки и сообщения пишутся в журнал ноута.
3. Запуск с runner = `auto` молча идёт на ноуте. Ручной запуск с явным
   runner = server открывает диалог «Нет связи с Сервер…» и кнопки
   `[Запустить на ноуте] [Ждать сервер в очереди]`.
4. Сервер всё это время продолжает свои задачи.
5. Дома узлы видят друг друга и обмениваются журналами. Новые задачи и
   сообщения обеих сторон просто появляются. Совпавшие `MSG-NNN` получают
   суффикс (5.3), совпавший `TASK-N` с более поздним созданием —
   следующий свободный номер (раздел 6). Если поле одной задачи меняли обе стороны, выигрывает поздняя
   правка, а проигравшая видна в треде и в списке конфликтов с кнопкой «Взять
   другую версию».
6. Задачи, ждавшие сервер в очереди, уходят на сервер.

### 14.3 Двойной запуск задачи

- **Узлы в сети.** Второй запуск отклоняется с `RUN_ALREADY_RUNNING` (раздел 7).
- **Во время разрыва.** TASK-N запущена и на ноуте, и на сервере. Каждый
  узел пишет свой ключ дескриптора, конфликта по нему нет.
  1. После слияния в дескрипторе два запуска одного поколения → `RUN_DUPLICATE`
     на карточке и в треде.
  2. Если оба ещё идут, оба продолжают работать. На карточке «выполняется на
     двух узлах» и кнопки остановить один из них.
  3. Ветка сервера — `kanban/TASK-N`, ветка ноута — `kanban/TASK-N@laptop`.
     Правило: без суффикса остаётся ветка запуска с меньшим `(hlc старта,
     node_id)`. Обе ветки передаются на оба узла.
  4. `status` задачи сливается по LWW. В Review человек выбирает ветку для
     landing, вторая остаётся до Done или abandon.

### 14.4 Выключение runner посреди задачи

- Сервер штатно выключили: `bye` → у запуска `RUN_NODE_POWERED_OFF` «Прервано:
  Сервер выключился в 03:40».
- Сервер пропал без `bye`: `RUN_NODE_UNREACHABLE`.
- Сервер вернулся: crash-restart по существующим правилам
  (`orchestration.auto_restart`), иначе предложение перезапустить на ноуте.

### 14.5 Дом обесточен: телефон автономно

1. Ноут выключен, дома нет света или интернета: server недоступен ни по
   LAN, ни по tailnet. На телефоне путь до сервера `none`; ошибок нет, шапка
   «Офлайн с {since}».
2. Задачи создаются с локальными номерами (раздел 6). Ответы, правки и треды пишутся в журнал телефона.
3. Запуск `auto` молча идёт на телефоне (`runner` резолвится в имя телефона).
   Клон уже есть после «Подготовить к поездке», иначе берётся из remote; без
   remote — `SYNC_NO_REMOTE`. Ветка `kanban/TASK-N` пушится в remote.
4. Если есть интернет, но нет сервера, телефон пишет операции в git-relay; ноут
   подхватит их, даже если сервер ещё лежит.
5. Сервер вернулся: по любому пути журналы сливаются по разделу 5,
   совпавшие номера задач перенумеровываются (раздел 6), ветки уже лежат в remote. Задачи,
   ждавшие сервер, уходят на него.

### 14.6 Телефон через tailnet при вендорском VPN

1. На телефоне включён вендорский VPN (единственный VpnService). kanban4ai в
   режиме `managed` поднимает userspace-`tailscaled`; его трафик идёт через
   вендорский VPN как трафик обычного приложения.
2. Синк ходит к `kanban-server.<tailnet>.ts.net:7420` через SOCKS5
   `127.0.0.1:1055`. Статус сервера: `ONLINE`, путь «tailnet, напрямую» или,
   если UDP закрыт, «tailnet через DERP».
3. Запуск `auto` уходит на сервер, лог читается live-follow, ответ на вопрос
   агента — операция журнала, сервер будит агента (раздел 7).
4. Android убил sidecar: на следующем тике он поднимается; если не
   поднимается — `NET_TAILSCALE_SIDECAR_DOWN`, синк переходит на relay, а
   запуск `auto` — на телефон.

### 14.7 E2E-проверка (TASK-424)

`sh scripts/e2e-sync.sh <kanban4ai> [workdir]` запускается только на тестовой
VM (passwordless sudo). Server, laptop и mobile работают в своих network
namespace, соединённых с server через veth. Mobile — outbound-узел с синком из
`kanban daemon`. Сон моделируется так: `bye sleep`, SIGSTOP serve и
отключение линка. Поездка — отключение линка при живых узлах. Выключение —
`bye shutdown` и SIGKILL всех процессов узла; в 14.5 ещё и отключение линка.
Агент заменён скриптом-заглушкой.
Реализованное поведение проверяется строго (`FAIL`), пункты незавершённых
задач печатаются как `PENDING <task>`; с `STRICT=1` они тоже валят прогон.

Прогон 2026-10-12 на VM 103 (45 с) охватывает 14.1–14.4 и часть 14.5 (телефон
без сервера создаёт задачи из резерва, после включения три реплики сходятся):
33 ok, 0 FAIL, 5 PENDING.

вариантами, ожидание явного server и запуск на сервере после его возвращения.
Полный E2E всё ещё имеет один FAIL в 14.4: после двойных запусков

- TASK-419: при живой связи второй запуск на другом узле не отклоняется.
- TASK-420: закрыто — `alternatives`, очередь выбранного узла и запуск после его

- TASK-421: коды узла/backend/repository реализованы; проверки поколения,
