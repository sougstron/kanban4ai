# Аудит производительности (TASK-391, 2026-10-09)

Цель — найти, что грузит CPU в фоне, раздувает память и замедляет открытие
проектов, особенно при многочасовой работе TUI. Ниже — замеры на живом сторе
(21 проект, 1 790 задач) и список проблем по приоритету. П. 1 и следующие
четыре согласованных изменения (2, 3, 4, 7) реализованы в TASK-391.
Остальные пункты ниже — предложения, а не обещание, что вся нагрузка устранена.

`kanban daemon` добавляют столько же.

Настоящий экран Projects показал те же имена, счётчики и флаги; `q` завершил

`compact-threads --all-projects` на копии: Balanceir/TASK-125 — 26 678 → 15

Затем миграция применена к рабочему стору после копирования 19 каталогов
тредов в `.kanban/backups/TASK-391/store/` проекта kanban4ai. TASK-125:

Финальный runtime smoke также проверил внешний rename на Projects,

Запись, дедупликация board-note и compaction защищены блокировкой доски.


## P0 — основные источники нагрузки

### 1. Каждый TUI раз в 5 с «прокачивает» все проекты стора — **сделано**

Исправлено в TASK-391 (`core/daemon.rs`):
- `shared_tick`: такт стора идёт под `<store>/pump.lock`, mtime файла —
  отметка последнего такта. Пока другой процесс качает или его такт моложе
  своего интервала, такт пропускается. N TUI + демон качают стор один раз.
- Пропуск тихих проектов: после полного такта запоминается отпечаток
  проекта (`stat` задач, сессий, `config.yaml` и глобального конфига) и
  ближайший дедлайн (таймаут heartbeat, конец ожидания, `restart_at`,
  `launch_at`). Пока ни то ни другое не сработало, проект не качается.
  Задача в очереди, ждущая слот, держит доску «занятой»; раз в минуту
  каждый проект качается всё равно (`QUIET_BACKSTOP`).

Замер на копии стора (19 проектов, `daemon --interval 5`, установившийся
режим): 1,79 с CPU за 45 с → 0,26 с, то есть ~4 % ядра → ~0,6 %.
Не сделано из этого пункта: один снимок задач на такт и удаление повторных
`check_sessions`/`due_*` в `dispatch_queue` — теперь это стоит только на
тактах с изменениями, выигрыш небольшой.

Исходное описание:
`App::pump_store_throttled` (`src/tui/app.rs:3200`) → `daemon::tick`
(`src/core/daemon.rs:78`) для всех 21 проекта. Для каждого проекта:

- `Operations::for_project` создаёт новый `Config`, поэтому конфиг заново
  читается, парсится из YAML и валидируется на каждом такте;
- `sweep_deferred_cleanups` (`operations.rs:4199`) берёт блокировку доски и
  разбирает **все** задачи, включая архив (`list_tasks(None)`);
- `dispatch_ready_dependents` (`operations.rs:2074`) снова разбирает все задачи;
- `check_sessions`, `due_restarts`, `due_launches` вызываются в `pump_project`,
  а потом ещё раз внутри `dispatch_queue` (`scheduler.rs:229`); плюс
  `Slots::measure` — это ещё несколько сканов `in_progress`/`todo` и
  `sessions/*.yaml`.

Скорее всего, этого достаточно, чтобы объяснить «фоново грузится CPU».
N открытых TUI плюс демон делают одну и ту же работу N+1 раз.

Что сделать:
- **Один насос на стор.** TUI берёт `daemon.lock` через `try_lock` без
  ожидания; держатель блокировки (демон или первый TUI) качает стор, а
  остальные TUI качают только свою доску или не качают совсем.
- **Дешёвый пропуск неизменившихся проектов.** Кэшировать по проекту
  отпечаток (`tasks_fingerprint` + mtime `sessions/`) и ближайший дедлайн
  (`restart_at`, `launch_at`, `wait_until`, `last_seen + heartbeat_timeout`).
  Если отпечаток не изменился и ни один дедлайн не наступил, проект
  пропускается. Большинство проектов простаивает, так что такт станет почти
  бесплатным.
- **Один снимок задач на такт.** Задачи загружаются один раз и передаются в
  `sweep`/`ready_dependents`/`due_*`/`dispatch`; повторные `check_sessions`,
  `due_restarts` и `due_launches` внутри `dispatch_queue` убрать. `sweep`
  достаточно смотреть `review`/`done`, архив можно не трогать.
- Чужие проекты качать реже (30–60 с), а открытую доску — как сейчас.

### 2. Экран Projects пересканировал все проекты в UI-потоке — **сделано**

`ProjectCache` в `tui/projects.rs` независимо кэширует task-счётчики,
активные сессии и `tui.name` по файловым отпечаткам. Heartbeat не вызывает
разбор task frontmatter. Registry и существование work folder проверяются
заново; удалённые проекты вытесняются. Ожидания пересчитываются по часам,
без ожидания изменения файла.

Первый кадр строится из registry; статус отмечает загрузку счётчиков.
Первый и последующие сканы идут на worker-потоке, одновременно не больше
одного. Завершённые потоки join-ятся, при выходе последний скан дожидается
завершения. Rename/delete/path-change инвалидируют старый результат;
выбор проекта сохраняется по id даже при смене сортировки.

Исходная проблема:
`App::tick` → `reload_if_changed` при `!has_board` безусловно вызывает
`refresh_projects` (`app.rs:2894`) → `projects::scan_counts`
(`tui/projects.rs:182`). Для каждого проекта читаются и парсятся через
serde_yaml **все** неархивные задачи (сейчас 673 файла), загружается полный
`Config` ради `board_display_name` (`migrate.rs:31`) и все сессии. Выходит
~100–150 мс блокировки ввода каждую секунду: список подтормаживает, а проекты
«долго открываются».

Что сделать: пересчитывать строку только при изменении её отпечатка
(`tasks_fingerprint` + mtime `sessions/` + mtime `config.yaml`); вынести скан
в фоновый поток; флаги (`review_unseen`, `has_questions`, `run_phase`,
`restart_at`) искать построчным поиском по frontmatter без полного YAML.

### 3. Раздутые треды после runaway-цикла cleanup — **сделано**

Добавлена команда `kanban compact-threads [TASK-ID] [--all-projects]`.
Она схлопывает только последовательные одинаковые `agent_step` от kanban
со счётчиком `×N`, не удаляет агентский/пользовательский контекст и сохраняет
сообщения, на которые уже отвечали. Cleanup retry теперь хранится в
`Task.cleanup_retry_at`, а последний board-note дедуплицируется по дисковому
треду, поэтому новый процесс не сбрасывает защиту.
Интервал задаётся `thresholds.deferred_cleanup_retry_interval` (600 с
по умолчанию). Sweep не читает архив и собирает cwd процессов один раз,
только если есть кандидат на cleanup (заодно исправлен п. 13).

Исходная проблема:
Коммит 4d6b89a остановил новую лавину, но:
- уже раздутые файлы остались: 11,8 МБ и 4,3 МБ. Каждое открытие детали,
  сборка промпта, `save_task` и пост в такой тред стоят 0,3–1 с;
- дедупликация и бэкофф хранятся **в памяти процесса**
  (`cleanup_failures`, `operations.rs:5951`). Новый процесс (`agent-exit`,
  перезапуск TUI или демона) снова постит ту же заметку, а каждый процесс
  раз в 10 минут гоняет git заново.

Что сделать: одноразовая миграция, схлопывающая подряд идущие одинаковые
`agent_step` от `kanban`; хранить сбой cleanup на самой задаче (текст и
время), а не в статике процесса; общий предохранитель в `post_queue_note`:
не постить, если последнее сообщение треда с тем же телом.

### 4. Повторный разбор треда и квадратичный merge при записи — **сделано**

При неизменённой rev `save` проверяет верхнеуровневый `rev:` без повторного
YAML-разбора. `post` возвращает сообщение из записанного снимка без нового
`get_message`/`load`. `save_task` не синхронизирует task-message, если описание
не изменилось (имя туда не входит). Merge использует `HashMap` вместо поиска
`position`: O(n) поиск плюс O(n log n) сортировка, без клона id на сравнение.

YAML и optimistic merge сохранены для совместимости. Snapshot base и
сериализация целого треда остаются; автоматическое удаление агентских
сообщений и переход на JSONL не вводились.

Исходная проблема:
`post_with_origin` (`core/thread.rs:164`) делает `load` → `save`, а `save`
снова делает `load`, клонирует тред, вызывает `merge_threads` с O(n²) поиском
по `position` и сериализует. После этого `get_message` делает третий `load`.
`Storage::save_task` (`storage.rs:275`) на **каждое** сохранение задачи
вызывает `update_task_message`, то есть полностью разбирает тред, только чтобы
сравнить тело. `snapshot_base` держит в памяти вторую копию всех сообщений.

Что сделать: `save` возвращает записанное сообщение без повторного `load`;
`update_task_message` вызывать только при изменении title/description;
`merge_threads` перевести на `HashMap` по id; ограничить число сообщений
`agent_step`. Если формат можно менять — append-only JSONL.

## P1 — отрисовка и перезагрузка в TUI

### 5. Полная перерисовка на каждое движение мыши
`EnableMouseCapture` в crossterm включает режим 1003 (any-motion). Каждое
движение мыши — это событие, полный `board::ui` и захват экрана. На детали
(`detail.rs:139-150`) на каждый кадр:
- `thread_lines` строится дважды (весь тред и весь тред без последнего
  сообщения);
- текст переносится примерно 4 раза: `line_count`, `wrapped_row_count` и
  `wrapped_text_region`, который клонирует **каждую** строку в отдельный
  `Paragraph`;
- `sanitize_terminal_text` проходит по всем телам сообщений;
- `task.clone()`;
- `task_has_backups` (`detail.rs:905`) рекурсивно обходит каталог.

На треде из 26 тысяч сообщений каждое движение мыши стоит сотни мс.

Что сделать: кэш строк и метрик переноса с ключом (rev треда, ширина,
выделенное сообщение, `hide_kanban`); склеивать подряд идущие `Moved` и
перерисовывать только при смене цели наведения; `has_backups` считать в
`load_detail`.

### 6. `RenderedScreen::capture` выделяет `String` на каждую ячейку каждого кадра
`app.rs:641`: на экране 250×60 это ~15 тысяч аллокаций на кадр. Варианты:
хранить клон `Buffer`/`CompactString` или захватывать экран лениво, только
когда начинается выделение текста.

### 7. Полная перезагрузка доски на изменение sidecars — **сделано**

`BoardStamps` разделяет задачи, сессии и треды. При изменении только sidecars
обновляются состояния сессий, вопросы и suggestion-counts, но задачи не
перечитываются. `TaskCache` при перестройке снимка разбирает изменившиеся
task-файлы по (путь, mtime, size); недавно записанные файлы перечитываются
консервативно из-за грубой точности времени. Архив берётся из того же
снимка. Открытая деталь обновляется при смене задач, собственного треда или
состояния её сессии, а не на каждый чужой heartbeat.

Из п. 8 сделан `DirEntry::file_type()` вместо дополнительного `is_file()`.
Редкий резервный опрос вместо секундного ещё не сделан.

Исходная проблема:
Каждый heartbeat, пост в тред или запись сессии меняет `tui_fingerprint`.
После этого `BoardSnapshot::load` (`app.rs:6501`) разбирает **все** задачи.
Архив разбирается и выбрасывается, потому что архивной колонки нет, затем
`refresh_archived_tasks` разбирает его ещё раз. Если открыта деталь,
`load_detail` заново читает тред, весь `stats/events.jsonl` и манифесты
provenance.

Что сделать: раздельные отпечатки для задач, сессий и треда открытой задачи.
Изменение в сессиях пересчитывает только `session_states`. Архив берётся из
того же снимка. Задачи кэшируются по (путь, mtime, size), и при изменении
перечитывается только изменившийся файл.

### 8. `tui_fingerprint` каждую секунду
`storage.rs:416`: на каждый файл задачи, треда и сессии — `is_file()` плюс
`metadata()`, итого ~1 600 `statx` в секунду. Нужен `DirEntry::file_type()`
(на Linux тип берётся из `d_type` бесплатно) и одна `metadata`. Раз уже есть
notify-watcher, опрос можно делать резервным и редким (раз в 10–30 с).

### 9. Поток на каждое событие файловой системы
`spawn_debounce_timer` (`tui/event.rs:220`) запускает новый поток на каждый
`FsChanged`. Атомарная запись даёт пачку событий (create/modify/rename), так
что получаются десятки потоков на каждую пачку. Лучше один debounce-поток
или `recv_timeout` в цикле событий.

### 10. Кэш `Config` клонирует весь конфиг на каждый вызов
`Config::loaded` (`config.rs:1854`) на каждом `load()`/`get_threshold()`/
`get_orchestration()` клонирует `LoadedConfig` (два полных `BoardConfig` с
serde `Mapping`). За такт таких вызовов десятки. При промахе `get_threshold`
парсит `DEFAULT_CONFIG_YAML` заново. Кэш инвалидируется только по mtime
глобального файла, поэтому правка `.kanban/config.yaml` из другого процесса
не видна (это ошибка корректности, не только скорости). Что сделать:
`Rc`/`Arc<LoadedConfig>`, ключ кэша из обоих mtime, дефолт хранить в
`LazyLock`.

### 11. `refresh_modal_after_catalog_warm` каждую секунду
`app.rs:3012` вызывает `config.load()` (то есть клон) на каждом тике, даже
без открытого диалога. Нужен ранний выход, когда `modal` пуст или все
каталоги уже прогреты.

## P2 — мелочи и долгий хвост

12. **Лимиты провайдеров обновляются в каждом процессе отдельно.**
    `limits::cached` читает дисковый кэш один раз за жизнь процесса
    (`DISK_LOADED`), поэтому каждый TUI и демон каждые 120 с сами запускают
    `sqlite3`/`codex`/`grok` и делают HTTP-запросы. Перед фетчем надо
    перечитывать `limits.json`, если он новее, и брать file-lock на время
    обновления.
13. **Обход `/proc` на каждую cleanup-задачу — сделано.** Sweep собирает
    cwd процессов один раз и переиспользует снимок для всех кандидатов.
14. **`TranscriptCache` никогда не вытесняет записи** (`telemetry.rs:174`).
    Состояние парсера остаётся для каждой когда-либо живой сессии, и за
    десятки часов это медленный рост памяти. Нужно удалять записи для
    неживых сессий.
15. **`estimate_session_tokens`** (`session.rs:383`) каждую секунду читает
    весь `.log` и прогоняет по нему 4 регулярки, если в транскрипте нет usage.
    Нужно читать инкрементально, как транскрипты, или реже.
16. **`stats::task_analytics`** читает весь `events.jsonl` (append-only,
    растёт бесконечно) на каждый `load_detail`. Можно кэшировать по
    mtime+size.
17. **Поток ввода** опрашивает с `poll(50ms)`, то есть просыпается
    20 раз в секунду в простое. В отдельном потоке достаточно блокирующего
    `event::read()`.
18. **Тик раз в секунду всегда перерисовывает кадр**, даже если ничего не
    изменилось. Стоит ввести dirty-флаг.
19. **`App::new` / `from_ops`** создаёт `Operations` дважды и дважды
    разбирает архив (см. п. 7).
20. **Диск.** Транскрипты не удаляются вообще (5,7 ГБ на стор), worktrees
    kanban4ai занимают 3 ГБ. Нужна политика хранения: сжимать или удалять
    транскрипты задач в Done/Archive старше N дней; чистить `target/` в
    приземлённых worktree.

## Порядок работ

1. Один насос на стор и пропуск неизменившихся проектов (п. 1). Это убирает
   основную часть фонового CPU.
2. Экран Projects по отпечаткам и в фоне (п. 2).
3. Миграция-схлопывание раздутых тредов и персистентный бэкофф cleanup
   (п. 3), затем дешёвая запись в тред (п. 4).
4. Кэш отрисовки детали и склейка событий мыши (п. 5–6).
5. Частичная перезагрузка снимка и кэш конфига (п. 7–11).
6. Остальное — по мере сил.
