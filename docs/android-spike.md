# TASK-431: userspace Tailscale в Arch/proot при вендорском VPN

Это ручной спайк перед managed-sidecar (TASK-433), не его реализация.
Прогон делает человек **на телефоне**. Локальная проверка скрипта на Linux
не доказывает работоспособность Android/proot/VPN.

Уже подтверждено человеком: `login.tailscale.com` открывается в браузере
телефона при включённом вендорском VPN (TASK-428 MSG-050). Это только шаг 0,
не подтверждение входа самого tailscaled или доступа к серверу.

## Статус и принятое решение

По ответу человека в TASK-431 MSG-010 прогон на телефоне отложен до конца
работ; дальнейшую разработку разрешено продолжать с допущением, что схема
будет работать. Скрипт и чеклист готовы, но результат на телефоне
**не проверен**: ни «работает», ни «DERP-only», ни «не работает» пока
не установлено. Это принятие риска, а не подтверждение транспорта.
Перед итоговой проверкой выполнить матрицу ниже и записать наблюдаемый
результат в context TASK-431; при неудаче использовать только git-relay.

## Подготовка

- Вендорский VPN включён всю проверку, включая смену сети. Не устанавливать
  Android Tailscale VPN: второй VpnService здесь не нужен.
- На сервере обычный Tailscale, он в том же tailnet. Запущен kanban4ai serve,
  слушает tailnet-IP на выбранном порту (обычно 7420); firewall и tailnet ACL
  разрешают телефону этот TCP-порт. `/api/v1/health` должен вернуть HTTP 200
  с `{"ok":true}` (пробелы несущественны), токен не нужен.
- Проверить этот endpoint с другого tailnet-узла, чтобы неисправность сервера
  не объявить провалом Android. Записать имя/IP и порт сервера.
- Две оболочки **одного Arch proot**, с одинаковым `$HOME`. Скрипт не запускает
  systemd, не создаёт фоновые процессы и не останавливает чужой tailscaled.
  SOCKS `127.0.0.1:1055` должен быть свободен.
- State хранится в `$HOME/.local/share/kanban4ai/net/tailscale`, каталог 0700,
  новые файлы создаются с umask 077. Не прикладывать state, ключи, полный URL
  входа или токены к треду. Логи перед отправкой просмотреть и обезличить.

## Запуск

Из корня checkout внутри Arch proot:

```sh
# Как root внутри proot; sudo не требуется. При необходимости обновления Arch
# сначала обычное полное pacman -Syu, не частичное pacman -Sy.
sh docs/android-spike.sh install

# Терминал A: остаётся занят, сохранить stderr/stdout при необходимости.
sh docs/android-spike.sh daemon
```

В терминале B того же proot:

```sh
sh docs/android-spike.sh up
# Открыть показанную ссылку в браузере телефона, войти в нужный tailnet.
# Не выключать вендорский VPN ради входа.
sh docs/android-spike.sh check
sh docs/android-spike.sh diagnose
```

При другом имени/порте задавать их для каждого check/diagnose:

```sh
SPIKE_PEER=kanban-server.example.ts.net SPIKE_PORT=7420 sh docs/android-spike.sh check
SPIKE_PEER=kanban-server.example.ts.net sh docs/android-spike.sh diagnose
```

`check` использует `curl --socks5-hostname`, поэтому DNS тоже идёт через
SOCKS, и отключает обход SOCKS через унаследованный `NO_PROXY`. Только HTTP
200 **и тело `ok: true`** считаются успехом. Скрипт не выносит итог автоматически.
При проблеме с коротким именем повторить с полным MagicDNS-именем, затем с
Tailscale IPv4 сервера, чтобы отделить DNS от недоступности транспорта.

## Матрица наблюдений

В каждом сценарии записать время, сеть, состояние VPN, PID/жив ли терминал A,
результат `check` (код выхода, HTTP/тело), `diagnose`, время восстановления.
Сохранить ошибки `operation not permitted`, netlink и логи daemon вокруг события.

1. **Вход.** Новый URL из `up` открывается в браузере телефона с VPN; после
   подтверждения `status` показывает авторизованный `kanban-phone`; `check`
   возвращает ожидаемое здоровье сервера. Повторный `up` после перезапуска
   daemon с тем же state не должен требовать нового входа (если ключ не истёк).
2. **Direct / DERP.** После трафика выполнить `diagnose`. `ping`/`status`
   показывают путь именно до сервера: прямой IP:port либо relay/DERP-регион.
   Первый ping через DERP может затем перейти на direct. `netcheck` показывает
   UDP/доступность DERP, но один `UDP: false` не доказывает DERP-only до пира.
   Проверить отдельно Wi-Fi и мобильную сеть, VPN оставить включённым.
3. **Выключенный экран.** В оболочке Termux **вне proot** взять
   `termux-wake-lock` (если телефон использует Termux). Записать настройки
   оптимизации батареи для Termux и VPN. Проверить `check`, выключить экран
   на 10 минут, включить, снова выполнить `check`/`diagnose`. Повторить без
   wake-lock (`termux-wake-unlock`) с тем же временем. Записать, жив ли daemon,
   сохранился ли VPN и восстановилась ли связь. Если другая оболочка — записать
   её механизм wake-lock; отсутствие механизма отметить, не считать проверенным.
4. **Phantom process killer.** Записать Android/прошивку, версию Termux/proot,
   настройки ограничения дочерних процессов (если известны). При обычном
   ограничении переключаться между приложениями и оставить телефон в фоне
   на 10 минут; наблюдать Termux `Process completed (signal 9)`, гибель proot
   и daemon. Wake-lock не гарантирует защиту от phantom killer. Не отключать
   ограничения через adb и не создавать fork bomb ради спайка. Если Android
   не убил процесс, отметить «естественное убийство не наблюдалось».
   Отдельно проверить **имитацию**: Ctrl-C в A, `check` в B должен провалиться;
   снова `daemon` в A, затем `check` в B — восстановление с тем же state.
   Это проверяет восстановление после остановки, но не настоящий SIGKILL
   Android. Если умер весь proot, открыть его заново и повторить daemon/check.
   Автоперезапуска здесь нет; он относится к будущему TASK-433.
5. **Смена сети / netlink Android 11+.** При живом daemon переключить
   Wi-Fi → мобильная сеть → Wi-Fi, VPN оставить включённым. После каждого
   перехода пробовать `check` сразу, через 30 и 60 секунд; собрать `diagnose`
   и логи. Не перезапускать daemon до этих попыток: важна самостоятельная
   реакция при недоступном netlink. При провале повторить после ручного
   перезапуска с тем же state и записать оба результата. Отдельно кратко
   выключить/включить сеть и проверить восстановление. Лог netlink сам по себе
   не провал, если реальный SOCKS-запрос после смены сети работает.

После проверки остановить daemon Ctrl-C в A; освободить wake-lock снаружи
proot. State оставить для проверки повторного входа либо удалить вручную
после завершения эксперимента; он содержит идентичность узла.

Заполнить, не заменяя наблюдения предположениями:

```text

Server name / port / preflight from another tailnet node: ...
Browser authentication from tailscale up: ...

Mobile network: health HTTP/body/exit, ping/status path: ...

Phantom killer: observed / not observed; restart and login persistence: ...
Network switches: recovery timings, netlink errors, restart needed: ...
Unverified scenarios: ...
Verdict: работает / DERP-only / не работает
Evidence and limitations: ...
```

- **работает**: вход и SOCKS health работают, direct наблюдался; условия
  фоновой жизни и восстановления указаны отдельно.
- **DERP-only**: вход и health работают, во всех проверенных сетях до сервера
  наблюдался только DERP. Это вывод для данной матрицы, не для всех сетей.
- **не работает**: после успешного server preflight на телефоне не удаётся
  пройти вход/достичь health либо соединение после обычных переходов сети
  остаётся неработоспособным. Указать этап, ошибки и эффект перезапуска.
- Непроверенные обязательные сценарии обозначать явно: итог предварительный,
  не закрывает риск sidecar. При неудаче запасной путь — **только git-relay,
  Sync 08 / TASK-440** (раздел 10.6 `docs/sync.md`); не отключать вендорский VPN
  и не обещать managed Tailscale до успешного прогона.

Результат передать агенту для записи через `$KANBAN_CMD context TASK-431 …
--source agent`. До прогона статус результата: **не проверено на телефоне**,
не «работает» и не «не работает».
